# Launch checklist

_Kone Tshivhinda & Claude, 26 Oct 2026. The one place that says what is done, what is being built, what only Kone can do, and what is deliberately later. If something is open and is not here, add it here. Detailed task ids are in [PHASES.md](PHASES.md); decisions in the ADRs._

**The goal this list serves:** ClearCut deployed so that **people use it with their own Anthropic key**, **TimeLex (and other products) can call it**, and **nobody's money or invoices are put at risk**. Not a standalone app: a service with a REST API, an MCP server, an SDK and a plain web page, over one Rust core.

## 1. Works today (built, tested, tried against the real API)
- Upload PDF, PNG, JPEG (streamed, size-limited, content-addressed, de-duplicated); page text, OCR (English, Afrikaans), page pictures; text-layer trust check (a lying text layer is detected and the page read as a picture).
- Reading every page with a model, cheapest first (Haiku, then Sonnet, Opus, Fable only when a deterministic check fails), budgets in rand (R5 a document, R100 a month), resumable, every call logged with its cost. **A missing tax goes to a person instead of up the ladder** (6 invoices: R5.36 before, R0.13 after).
- Deterministic checks in Rust (lines, VAT, totals, SA tax-invoice fields), events as the source of truth, narration with the number guard, report modes, JSON / CSV / Markdown export.
- **Review:** a person corrects and confirms a page the reader could not settle; recorded as theirs, no model call.
- **Delete:** a document, everything read from it and its file are erased for good (POPIA); a content-free record of the deletion stays.
- Tenants, API keys with scopes, row-level security, audit log; the web page (sign in, upload, list, report, review, delete); `docker compose up` on your own computer with the worker and database isolated.
- Your own key on your own computer (mode A): environment or file, never printed, never in the worker. **Each account's own key on a deployed service (mode B)**: stored encrypted, write-only, used per job.
- Prompt-injection handling: document text is data; flagged pages get a person's eyes before "done".

- **Anthropic terms**: confirm retention and zero-data-retention for the models in use (research 06 section 8: Fable 5.1 is 30-day retention).
- **Hosting and a domain**, when a hosted trial or service is wanted.
- **Which documents beyond invoices** (bank, payment-processor, supplier statements) for fee reconciliation (P2-21), and whose taxonomy for line categories (P2-22).

- **Attorney review** of the drafts in [docs/privacy/](privacy/README.md) (a notice, an operator agreement, the transfer to Anthropic outside South Africa) and the breach procedure.

## 5. Known limits today (so nothing is a surprise)
- Set `CLEARCUT_KEY_MODE=tenant-only` on any deployment: in the default `shared` mode the server's own key fills in for an account with none, which is right for your own computer and wrong for other people's money.
- One document is read at a time unless `CLEARCUT_RUNNER_CONCURRENCY` is raised (then at most one per account).
- If the server process is killed in the middle of a page, the model calls that page had already made (and been billed for) are not in the call log, so that account's spend is under-counted by at most one page's calls until the next month's sum. Each call being logged as it happens would close it.
- Local use binds the page to this computer only; a deployment adds HTTPS with `--profile https` ([DEPLOY.md](DEPLOY.md)). Files live on a local disk volume.
- A page confirmed through the MCP server is recorded as a person's confirmation, against the API key: ClearCut cannot tell an agent's "yes" from a person's. Give an agent a key with only the scopes it needs, and rely on the deterministic checks every confirmation still passes.
- If saving a review succeeds but queueing the finishing job fails, the document waits until a job is queued.
- A file whose deletion fails after its rows were erased is left behind (reported in the log) for a sweep that does not exist yet.
- Deleting a document is not locked against a job queued, or the same bytes uploaded again, in the same instant: the first makes that job fail on its foreign keys (nothing is written), the second can leave a row whose file is missing (reported as "file missing", fixed by uploading again). Both need a lock inside the database function; it goes into the next migration (item 1). An upload refused for quota removes its file at once, and an identical upload racing that removal can leave the same kind of row (re-uploading fixes it).
- Nothing is encrypted at rest in the database or file store: use disk encryption on the host.
- **Retention is 365 days by default** (`CLEARCUT_RETENTION_DAYS`; `0` turns it off). Age is counted from upload, so reading a document again does not extend its life, and the period is one for the whole server (there is no per-account setting). A document being read when the sweep runs waits for the next pass, an hour later. Erased means gone from the live system; **a document deleted by a person or by retention stays in older backups** until they expire.
- Each account is limited to 1 GiB of stored files (`CLEARCUT_TENANT_QUOTA_BYTES`) and 120 requests a minute (`CLEARCUT_RATE_LIMIT_PER_MINUTE`). The rate limit is counted in the server's memory, so it is exact for one server (what DEPLOY.md describes) and each extra server would allow its own.
- Search (`GET /v1/search`) matches the text of the stored events: supplier and recipient names, VAT and invoice numbers, line descriptions, due terms and dates. It does not match amounts or kind names, and it does not stem words (`Ndlovu` finds `Ndlovu`, not `Ndlovus`). There is no search index yet, so a very large account searches more slowly.
- **Duplicate detection is a conservative warning.** It compares exact printed facts: the supplier name, invoice number, invoice date and gross total must all be present and identical (a name differing only in case or spacing is not a match). Only documents that were uploaded **and read earlier** count, so a copy read before the earlier document has been read, or one still waiting for a page review, is not found (a document that ended `needs_review` after whole-document checks has its events and is compared). The lookup looks through the earlier documents that state the invoice number (no index on the number yet), and the warning is recorded on the first read, not recalculated by a later re-read. If the lookup itself fails, the document still finishes and the warning is skipped (logged), so an advisory check can never cost a read. If the earlier document is later erased, the warning keeps its id.
