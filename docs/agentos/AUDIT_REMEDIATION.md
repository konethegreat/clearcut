## Detailed Diagnosis

### 1. `RUSTSEC-2026-0459` - `libsqlite3-sys 0.37.0`
- **Advisory:** `libsqlite3-sys` via C SQLite CVE-2026-119375 (2026-10-30). Fixed in `>=0.39.0`.
- **Dependency path:** `Cargo.lock` includes `libsqlite3-sys 0.37.0` under `sqlx-sqlite 0.9.0`, which is listed as an optional dependency of `sqlx 0.9.0` and `sqlx-macros-core 0.9.0`.
- **Exposure:** None in compiled artifacts. ClearCut crates (`clearcut-store`, `clearcut-admin`, `clearcut-jobs`) only enable `sqlx` features `runtime-tokio`, `postgres`, `migrate`, and `macros` - never `sqlite`. `cargo tree --target all -i libsqlite3-sys` confirms `libsqlite3-sys` is not active in the build graph, but `cargo audit` scans every entry in `Cargo.lock` regardless of Cargo feature flags.
- **Remediation:** Test `cargo update -p libsqlite3-sys` in the next Phase 1 PR. Because `0.37.0` to `0.39.0` is a semver-breaking bump for `0.x` crates, `sqlx-sqlite 0.9.0` will likely constrain `libsqlite3-sys` below `0.39.0`. If `sqlx` cannot resolve `>=0.39.0`, add a temporary documented exception for `RUSTSEC-2026-0459` in `.cargo/audit.toml` and `docs/THREAT-MODEL.md` section 5 noting that the `sqlite` feature is disabled and `libsqlite3-sys` is never compiled or linked.

### 2. `RUSTSEC-2026-0462` - `rmcp 3.7.0`
- **Advisory:** Unbounded response body buffering in Streamable HTTP clients (2026-11-05). Fixed in `>=3.9.0`.
- **Dependency path:** Direct dependency of `crates/clearcut-mcp` (`rmcp = { version = "3.5.1", features = ["server", "macros", "transport-io"] }`, locked at `3.7.0`).
- **Exposure:** Low/none in current code because `clearcut-mcp` only enables `server`, `macros`, and `transport-io` (serving over `rmcp::transport::stdio()`), not the Streamable HTTP client.
- **Remediation:** Upgrade `rmcp` to `3.10.0` (covered by open Dependabot PR `#148`), verify `crates/clearcut-mcp` compiles and passes tests, and remove the vulnerability cleanly without an exception.

### 3. `RUSTSEC-2026-0429` - `zip 8.6.0`
- **Advisory:** `ZipArchive::extract` aborts the process on a symlink entry with a large declared size (2026-10-22). Fixed in `>=9.0.0`.
- **Dependency path:** `Cargo.lock` contains two `zip` versions:
  - `zip 9.1.2` (direct in `clearcut-export` and transitive via `rust_xlsxwriter 0.101.0`), which is already `>=9.0.0` and has an open Dependabot PR `#149` to `9.5.1`.
  - `zip 8.6.0` (transitive via `docx-rs 0.4.22` in `clearcut-export`), which triggers `RUSTSEC-2026-0429`.
- **Exposure:** None in production. `clearcut-export` uses `docx-rs` only to generate `.docx` files (`docx_rs::Docx` and `pack`) and `zip::ZipWriter` to write CSV bundles. `ZipArchive::new` is called only in unit tests (`crates/clearcut-export/src/tests.rs` and `src/register/tests.rs`) on self-generated bytes; `ZipArchive::extract` is never called.
- **Remediation:** Check whether a newer `docx-rs` release upgrades to `zip >= 9.0.0`. If not, add `RUSTSEC-2026-0429` to `.cargo/audit.toml` alongside `RUSTSEC-2026-0367`, `RUSTSEC-2026-0368`, and `RUSTSEC-2026-0369` with the same condition (revisit when `docx-rs` moves to `zip` 9), and document it in `docs/THREAT-MODEL.md` section 5. Also process Dependabot PR `#149` (`zip 9.5.1`) for the direct `zip 9.x` dependency.

### 4. `RUSTSEC-2026-0486` - `rustix 1.1.5` (Warning)
- **Advisory:** `xattr` functions mark unwritten bytes as initialized when given a zero-length buffer (2026-10-27). Fixed in `>=1.1.6`.
- **Dependency path:** Transitive dev-dependency only via `tempfile 3.27.0` (`[dev-dependencies]` in `clearcut-anthropic`, `clearcut-eval`, `clearcut-intake`, `clearcut-mcp`, `clearcut-objects`, `clearcut-pipeline`, `clearcut-server`).
- **Exposure:** Test-only; not present in production binaries and ClearCut does not invoke `rustix` `xattr` functions.
- **Remediation:** Run `cargo update -p rustix` to pull `>=1.1.6` (semver-compatible patch update) so `cargo audit` emits zero warnings.
