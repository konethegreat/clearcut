## 2026-10-30 (part 79) — a mixed page divides only the lines that bear VAT
**Done**
- **[ADR-0024](adr/0024-mixed-inclusive-pages.md) replaces ADR-0023's all-or-nothing rule.** On a page that says its amounts include VAT, each line is now treated by what it bears: a standard-rated line is divided at the profile's rate, while a zero-rated, exempt or out-of-scope line was charged no VAT, so its printed amount is already the net and it is read as printed with its own category. The refusal that made a common grocery slip unread is gone.
- **A silent line is still only assumed standard when nothing on the page contradicts it.** `not_shown` becomes standard while no line names a non-standard category, which keeps the old all-standard-or-silent case. A page that mixes a silent line with an explicit zero-rated or exempt line is still refused with one `amounts_include_vat` problem and no lines, because the silent line may or may not have been charged VAT.
- **The arithmetic is unchanged** for divided lines: per unit price, half away from zero, line total recomputed, printed line total ignored. A kept line is read the ordinary way, printed line total included, so the validator's quantity-times-price rule applies to both kinds on one page.
- **The review copy is more precise.** The `amounts_include_vat` sentence now says the standard-rated lines were divided by 1.15, since "the amounts" is no longer true on a mixed page. The page still goes to a person and still reports the problem.
- **Known limitation, recorded:** the text check is still page-level, so a kept zero-rated line's printed figures are not compared with the page text. Header figures and totals still are, and the page is reviewed. A per-line flag would need the extraction to remember which lines were divided, a larger shape question.
- **Tests:** a mixed page divides its standard line and keeps its zero-rated one; zero-rated, exempt and out-of-scope lines each read as printed; a mixed slip reconciles its net against its own totals; a silent line beside an explicit zero-rated one is still refused; a refused page reports no line problems. Core 654, whole workspace green against local Postgres, clippy and fmt clean; no shape, prompt or contract change.
- **Docs:** ADR-0024, a revision note on ADR-0023, the ADR index, ARCHITECTURE, CLAUDE.md and the LAUNCH universal-core row.
- **Shipped and deployed.** Squash-merged as #118 (`c6013b9`); the VM pulled it, rebuilt the server image, and `/health`, `/` and `/v1/whoami` answered as expected. The served `app.js` carries the "divided the standard-rated lines by 1.15" copy.
**Not done:** per-line text checking of derived amounts; a silent line on a mixed page; a second jurisdiction and how a document chooses it.

## 2026-10-30 (part 78) — prices that include VAT are divided out, and still meet a person

## 2026-10-30 (part 74) — a guard in front of the API, bytes that must match their type, and an alpha banner
**Done**
- **The limits now come before the key lookup.** `crates/clearcut-server/src/guard.rs` holds a per-address minute (300 requests) and a failed-credential budget (20 a minute) checked in `Authed::from_request_parts` before `authenticate`, so a flood of wrong keys costs a map lookup rather than a database query; at the budget the address waits 60 seconds and is answered 429 with `Retry-After`. The map is bounded at 65,536 addresses, oldest window dropped first, so a distributed flood cannot grow it without limit. Ten unit tests fix the exact boundary, the retry seconds (rounded up), the window rollover, independent addresses, the block and its expiry, and eviction.
- **Every route is now covered by a concurrency cap (503 with `Retry-After` when full) and a request timeout (408),** applied outermost in `finish`, so they cover authentication and the handler together. The socket peer is used as the address, or the last `X-Forwarded-For` entry when `CLEARCUT_TRUST_PROXY` is on, because Caddy appends the address it saw; a fake earlier entry cannot choose it.
- **Every answer carries** `X-Request-Id` (a well-formed caller id kept, anything else replaced with a UUID, so no caller text reaches the log), `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, and the cross-origin opener and resource policies. One access line per request records method, path, status, duration, address and id, at ERROR for 5xx, WARN for 4xx, DEBUG for `/health`; it never records a key, a body or document text.
- **An upload must start with the bytes its type promises.** Intake reads the first 64 bytes before anything is stored and refuses a PDF that does not start `%PDF-`, a PNG/JPEG/TIFF without its signature, or XML that does not reach `<` after an optional byte-order mark and whitespace; the bytes are put back in front of the stream. A mismatch is `415` with its own message, and nothing is stored. The old test that uploaded arbitrary text under every type now uses real signatures, and a new test proves a disguised file leaves no row and no file.
- **An Alpha strip sits above the bar on every screen,** static markup outside the app shell so the demo and every route show it: "ClearCut is in active development. Check every figure that matters against the original document." A web test keeps it there and checks it comes before the shell.
- **Settings and docs:** six settings with startup validation (`.env.example`, `docker-compose.yml`, DEPLOY and ADMIN describe them), `CLEARCUT_TRUST_PROXY=1` only behind Caddy, THREAT-MODEL threats 2, 3, 7 and 11 and the open gaps updated, and LAUNCH gained section 6, the four tracks that were split off the first ask (edge protection and a domain, scale readiness, universal invoice core, legal and trust) with what starts each.
- **Tests:** 10 guard unit tests, 9 router tests for the guard (limit before the authenticator, failure budget from wrong and missing keys, 408, 503, headers, request id, and the deliberate no-address case), 2 intake signature tests and the disguised-file test. Server 119, intake 40, server binary 6, all passing against Postgres.

## 2026-10-29 (part 69) — a long invoice's carried chain is checked and recorded (ADR-0022 step 2)
**Done**
- **The chain is checked only where the document prints both sides.** After `assemble`, `validate` reads the per-page carried pairs in page order and compares page N's carried-forward figure with page N+1's brought-forward figure. It is exact to the cent, it only compares **adjacent** pages (a gap in the page numbers makes no claim), and it only compares when both figures were printed; a missing side means no finding. A mismatch is `Finding::CarriedBalanceMismatch` (Critical), so the document still ends `needs_review` and the job `succeeded` with a person-readable reason; a clean chain changes nothing and the document ends `done`.
- **Two new event kinds, both Totals.** `balance_stated` (Info) records each printed figure with its role (`brought_forward` / `carried_forward`) and its page; `balance_mismatch` (Critical) records the page that carried the figure and both amounts. ## 2026-10-28 (part 63) — a per-account storage quota and request rate limit (threat 11)
**Done**
- **Storage quota**, `CLEARCUT_TENANT_QUOTA_BYTES` (default 1 GiB): an account's documents together may not exceed it. Checked three times, each cheaper than the last line of defence: a declared `Content-Length` over the remaining room is refused with `507` **before the body is read** (unless the account already holds a document of that size, which may be the repeat itself); the byte stream is capped at the remaining room so an upload that lies about its length stops as it arrives and leaves no partly-filled disk; and the store inserts the document only through `add_document_within`, which takes a **per-tenant advisory lock**, sums `documents.byte_size` and refuses atomically, so two uploads cannot both take the last room. Deleting a document frees its room with no extra work. A repeat upload of identical bytes stays free and succeeds even when the account is full, because it adds no bytes: a declared length over the room is let through when the account already holds a document of exactly that size, which is the only way a repeat can be recognised before its content is read.
- The pre-check is deliberately best-effort: if the database cannot be read, the quota is treated as unknown and the insert decides, which keeps the existing promise that a database failure leaves the uploaded file in place for a retry. A file that was stored and then refused by the quota is deleted again, since nothing refers to it (a failed removal is logged): an identical upload racing that removal can leave a row pointing at a missing file, re-uploading fixes it, and it is the same narrow race as erasing a document while uploading it.
- **Rate limit**, `CLEARCUT_RATE_LIMIT_PER_MINUTE` (default 120): a fixed-minute window per account, kept in the server's memory and checked **after** authentication (so a bad key still gets the identical `401` and cannot probe), answering `429` with `Retry-After` in whole seconds and the same number in the body. Refused requests do not extend the window.
- **The MCP server's `wait_for_document` honours the limit**: it polls only the document (the latest job once, at the end), and on a `429` waits as `Retry-After` says instead of failing. One 60-second wait at the old 2-second poll made 60 requests (two per look), half the allowance; two concurrent waits used it all.
- `POST /v1/documents` answers `507 Insufficient Storage` with `used_bytes` and `quota_bytes`; every route that needs a key can now answer `429`. `contracts/openapi.json` regenerated; the `429` response documents the `Retry-After` header.
- **No database migration**: the quota is the sum of a column that already exists, and the lock is an advisory lock inside one transaction.
- Written test first (watched each fail): 6 for the limiter (exact limit, seconds rounded up, a new window, per-account separation, a refusal that neither counts nor extends), 3 HTTP (429 plus `Retry-After`, another account unaffected, a bad key refused as `401` before any allowance), 7 store (sum per tenant, the size lookup, over-quota refused, exactly-full accepted, **two concurrent uploads with one winner**, a duplicate accepted when full, one tenant's quota not limiting another) and 6 intake (refused before the body is read, a lying length still capped, exactly-full accepted, a repeat accepted when full, a new file of that size refused and removed, per-account); the MCP wait test was added in review. To prove the advisory lock earns its place, removing it made the concurrency test fail with two winners.
- Full gate: `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace` against the local Postgres: **1,939 passed, 0 failed, 21 ignored**.

## 2026-10-21 — P1-02 part 1: `clearcut-objects` (object storage)
**Done** (own branch and PR; tests first; 19 tests; workspace now 191 core + 19 objects + 23 store + 3 server)
- New crate `clearcut-objects`: `ObjectStore` trait (`put`, `open`, `exists`, `delete`) and `LocalDisk`. A key is `tenants/<uuid>/documents/<sha256 hex>`: **content-addressed and tenant-scoped**, so the same upload twice is stored once, and two tenants never share an object. `ObjectKey` can only be built from a tenant and a hash, or parsed back in exactly that canonical shape (lowercase hyphenated UUID, lowercase hex), so a filename, `..`, an absolute path, a backslash or an odd UUID form can never reach the filesystem.

Failed, oversized or empty uploads leave nothing behind; simultaneous identical uploads all succeed and leave one intact object.
- Mutation-checked six rules (limit boundary, empty check, temp cleanup, canonical UUID form, lowercase hex, tenant in key). The UUID-form mutation initially survived, which led to extra test cases for uppercase, braced, `urn:` and simple-form UUIDs.

**Decisions / push-back**
- **Not built yet, on purpose:** the upload endpoint (an unauthenticated write endpoint is the wrong thing to ship; it waits for P1-04), resumable/chunked uploads (a design of its own: sessions and partial state), and the S3/MinIO implementation (arrives with the Docker stack, P1-07; the trait is shaped for it).
- Content addressing means a delete removes the object for every document of that tenant with the same bytes; the store layer must not delete an object another document row still references (decide with the upload flow).
- Virus/malware scanning of uploads is not designed yet; uploads are treated as untrusted bytes and nothing here executes or parses them.

## 2026-10-20 (part 4) — P3-03 event derivation
**Done** (own branch and PR, stacked on the P2-08 PR; tests first; core now 181, workspace 184)
- `extraction::derive_events(&Extraction) -> Result<Derived { validation, events }>`: runs `validate`, then derives events in a fixed order: supplier, each line (as printed), VAT per tax category present, stated totals, due date, credit-note reference, then one event per finding.

**Decisions**
- A fact with amounts in two currencies cannot be an event of its own kind, so it becomes a compliance-issue event with the same ID instead of an error. An invalid location (bad bounding box) from the extractor *is* an error: better a visible rejection than quietly losing citations. The orchestrator should treat that as `needs_review`.
- A line in the wrong currency is not narrated as a line; its finding explains why. A line with a wrong total is still narrated as printed, beside an event saying it is wrong.
- **By-party view dropped** (was deferred in P3-02): it needs a party identity that survives across documents, which belongs with storage.
- Recipient is not yet an event (no `RecipientIdentified` kind); add when a use needs it.

**Done**

- **P3-06 number guard** (`clearcut-core::narration::guard`), tests first, on its own branch and PR. 36 new tests; core now 114, workspace 117. Mutation-checked: disabling the date check or the sign handling makes tests fail.
  - `check(narrative, events)` returns violations; `guard(candidate, events)` returns the candidate if clean, else template sentences for the cited events (once each, in citation order).
  - Per sentence, the allowed facts are the figures and dates in the template wording of the cited events plus their own dates. Because it reuses the narrator's wording, guard and narrator cannot disagree on formats.

**Decisions / findings**
- Deliberately strict: `R1500` (no decimals), `R15 000.00` with an ordinary space, abbreviated months and `1,500.00` are rejected. A false rejection only means falling back to template text; a false acceptance would put a wrong number in a financial narrative.
- Known limits, written into the module docs: numbers written as words ("ten") are not seen, and a sentence can mislead while every figure in it is real. Template wording of facts is the main defence; the guard is the second.
- `INV-0042` scans as `-0042` (a hyphen before digits reads as a sign). That is consistent between template and candidate, so it only matters if a rewrite drops the hyphen, which is then rejected (safe direction).
- A first sed-based mutation silently did not apply and looked like a passing test; re-did it with a real edit. Lesson: confirm a mutation actually changed the file.
