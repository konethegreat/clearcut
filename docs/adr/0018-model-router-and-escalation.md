# ADR-0018: The model router and the escalation ladder

Status: **Accepted** (approved by Kone Tshivhinda, 2026-10-25, with all eight recommended answers below; for question 6 the per-document cap grows with the pages) · Date: 2026-10-25 · Deciders: Kone Tshivhinda, Claude
Task P2-14, with the page-reading half of P2-06 and the per-call log of P2-15. Builds on [ADR-0005](0005-model-strategy-escalation.md) (the ladder), [ADR-0011](0011-bring-your-own-anthropic-key.md) (the user's key, budgets, errors), [ADR-0012](0012-anthropic-adapter.md) (the adapter and its failures), [ADR-0013](0013-model-facing-reading-shape.md) (what the model returns), [ADR-0014](0014-context-pack-builder.md) (what is sent), [ADR-0017](0017-document-analysis-stage.md) (how each page is read) and [research 06](../research/06-anthropic-api.md) (the API's facts). Design only; nothing is built until this is approved. **No model has been called in the whole project yet**, so every number below that depends on real model behaviour is a starting value for the gold set to correct.

## What it is
Every piece the router needs exists and is tested, and nothing yet **decides what to do with them**:

```text
page_reads (ADR-0017)  ──►  render, text, mask (worker)  ──►  context pack (ADR-0014)  ──►  provider (ADR-0012)
   route per page                                                                                   │
                                                                                                    ▼
 next rung ◄── escalate ◄── assess: conversion problems + validate + text check ◄── PageReading (ADR-0013)
     │                                         │ accept
     └── top rung fails, budget or caps hit ───┴──► needs_review (with the best draft)
```

The router reads **one page at a time** and decides, from deterministic evidence only, whether the reading is good enough to keep, should be tried again by a stronger model with a report of what was wrong, or should go to a person. It ends every page in one of two states, `read` or `needs_review`, never a third, and it cannot loop for ever or spend more than it was allowed.

## 1. Where the code goes
| Part | Where | Why |
|---|---|---|
| The ladder as data (`RouterPolicy`: rungs, effort, output caps, image sizes, call caps), the **assessment** (a reading is accepted, or escalated for a named reason), the **page state machine**, the evidence-based confidence | `clearcut-core::escalation` | These are business rules: pure, no I/O, no clock, tested exhaustively, and tuned on the gold set without touching an async runtime |
| Prices and the cost of a call in rand (`Cost`, a price table keyed by model id with the date it was read) | `clearcut-core::cost` (the first half of P2-12) | The router must check budgets, so it needs the arithmetic; integer units finer than a cent, rounded up when charged to a budget |
| The async driver for one page: gets the picture and text from the worker, builds the pack, calls the provider, feeds the answer to the state machine | new crate `clearcut-router` | Generic over `ModelProvider` and `DocumentProcessor`, so it is tested with `FakeProvider` and `FakeWorker`. **No database.** |
| The read stage of the job: pages in order, saving each result, budgets, resuming | `clearcut-pipeline` | Persistence and the job stay where they are |

**The state machine is the design's centre.** It is a plain value: `PageReader::start(policy, route, page_of_n) -> Step`, and `step.on_outcome(outcome) -> Step`, where a `Step` is `Call(CallPlan)` (use this rung, this effort, this report) or `Done(PageOutcome)`. The async driver only loops "do what the plan says, report what happened". Three things follow: it is testable without any async code or network; **termination is a property we can test** (every possible sequence of outcomes ends within the caps, checked over generated sequences); and a later **Batch driver** (cheaper, results within 24 hours) can run the same machine in rounds, all pages at the first rung in one batch, then the failures at the next, without a second copy of the rules.

## 2. The ladder
Haiku 5.5, Sonnet 5.5, Opus 5.5, Fable 5.1, then a person (ADR-0005). As data:

| Rung | Model id | Effort | Largest answer | Page picture | Default |
|---|---|---|---|---|---|
| 1 | `claude-haiku-5-5` | medium | 16 000 tokens | 150 dpi, 2 000 px | on |
| 2 | `claude-sonnet-5-5` | medium | 12 000 | 150 dpi, 2 000 px | on |
| 3 | `claude-opus-5-5` | high | 8 000 | 200 dpi, 2 576 px | on |
| 4 | `claude-fable-5-1` | high | 4 000 | 200 dpi, 2 576 px | **off** (Kone, ADR-0011: it keeps data for 30 days and may be refused by the account) |

- **Effort is fixed within a rung** (a changed effort breaks the prompt cache) and is the only thinking control (`thinking` omitted, never `budget_tokens`). A larger picture on the upper rungs is a deliberate part of "resource completeness": a page that failed twice may simply have been read too small. The picture comes after the cache breakpoint, so this costs input tokens and nothing else.
- **The largest answer includes the model's thinking** and is also the worst-case bill of one call. See the budget rule (§6): it is why the upper rungs are smaller, so a single call can never cost more than a document is allowed. These numbers are the first thing a live run should check.
- **What the key can use** comes from the Models API (the free key check). A rung the key cannot use is skipped; a `ModelUnavailable` answer (a 403/404 on the model, or Fable refused for its retention rule) skips the rung and is remembered for that tenant for an hour, so the next document does not pay to find out again.
- The policy is validated when it is built (rungs in order, at least one on, each rung's worst-case call within the document cap, caps above zero) and is read from operator configuration, never from tenant input.

## 3. When a reading is accepted, escalated or sent to a person
This is the rule of the whole feature, and it uses **only** evidence ClearCut can compute. Nothing the model says about itself, and nothing the page says, picks the next step.

**Accepted** when all of these hold:
1. the answer follows the schema and converts (`PageReading::into_extraction`) with **no problem on a critical field** (the list is the gold set's: invoice number, date, currency, supplier name and VAT number, the three totals, each line's quantity, unit price and total);
2. the **page-local arithmetic** passes: quantity times unit price equals the line total on every line, no zero or negative quantity, amounts in range, one currency;
3. the **text check** passes, where the page has trustworthy text (route `text_and_image` or `image_first`, OCR text on `image_only`): every amount the model read must occur as digits in the page's text (P2-13c, proposed in ADR-0013 §4). This is what catches a number the model invented, which arithmetic alone cannot, and it is free.

**Escalated** (to the next rung, with a failure report in ClearCut's own vocabulary, ADR-0014) when any of 1 to 3 fails, with one named reason: `reading_problems`, `line_arithmetic`, `totals_mismatch`, `text_check_failed`. A schema failure or a cut-off answer is handled first on the same rung (§5).

**Not a reason to escalate**, because a stronger model cannot fix it and escalating would burn money:
- findings about the **document itself**: a due date before the invoice date, a South African tax-invoice rule that the document breaks (`compliance_za`). They are recorded on the page and shown to the reviewer;
- a page with **no lines** or **no totals**: a terms page or a continuation page is allowed to have neither. Whether the *document* has them is decided after the pages are put together (P2-07).

**The totals check is page-local only for a one-page document.** On page 3 of 5 the lines may sit on pages 1 to 3 and the totals on page 5, so a page-local "lines do not add up to the printed total" would be a false alarm and would escalate a correct reading. Reconciling lines to totals across pages is P2-07's job; when it fails, it asks the router to **re-read** the pages it names at the next rung (`PageReader::resume(from_rung, failure_report)`). Which pages to re-read is P2-07's decision and is not made here.

**Not used, and why.**
- *The model's own confidence.* ADR-0005 listed it as a trigger, but the reading shape deliberately has no confidence field (ADR-0013: models state high confidence on wrong numbers). Confidence attached to a value comes from evidence instead: confirmed in the page text and arithmetically consistent, 950; consistent but unconfirmed (no usable text), 850; anything on a page that ended with open problems, 500 (below the gold set's review threshold of 800, so it is flagged). These are provisional constants for P2-09 to refine, and they do not depend on the tier.
- *Two independent passes and a vote* (also in ADR-0005). Every page would cost at least double. The arithmetic and the text check are the second opinion, for free. A second pass is kept as an option for the one place they cannot help, a critical value with neither text nor arithmetic behind it, and is added only if the gold set shows such a case being wrong.
- *A model as judge.* A judge reads the page too, so it is as open to injection as the reader, and it is not deterministic.

## 4. Where each page starts
**Every page starts at rung 1**, including scans and doubtful pages. ADR-0005 started messy scans at Sonnet. The arithmetic says otherwise: at the planning prices (research 06 §10, R18/USD) a Haiku attempt costs about R0.02 a page and a Sonnet one about R0.40, so trying Haiku first is cheaper whenever it succeeds on more than R0.02 / R0.40, which is 5% of such pages (Haiku first costs `0.02 + 0.40 x (1 - p)`, Sonnet first costs `0.40`). A failed Haiku attempt wastes two cents. The ADR therefore starts low everywhere and lets a per-route start rung be set from the gold set, if scans turn out to fail at Haiku nearly always. This is the one place I deliberately depart from ADR-0005's table.

What the route (ADR-0017) changes is **what is sent**, not where it starts:
| Route | Sent |
|---|---|
| `text_and_image` | the page picture and its text layer, labelled `text_layer` |
| `image_first` | the picture, and the text layer labelled `unverified_text_layer`: "where they disagree, trust the picture" |
| `image_only` | the picture, and OCR text labelled `ocr` if OCR was run, otherwise no text |

The third label needs one sentence in the cached rules, so the prompt text changes. `prompt-v1` has not been used for any real call, so, as ADR-0014 did before, it is edited in place and the golden file regenerated; the first live call is what freezes it.

## 5. What each failure does
The router **never retries a transport failure itself.** The adapter already retries inline twice (ADR-0012 §5) and the job queue retries after that (ADR-0008), so a third layer would multiply them. The router's own loop is only for quality (escalation) and for two answer-shape cases.

| What came back | The router does |
|---|---|
| A reading that fails §3 | escalate, with the failure report; the same rung is not tried again |
| `Truncated` (cut off at the answer cap) | once more on the same rung with the cap raised to the adapter's 16 000 (or the policy's ceiling); a second cut-off means the page is too dense for one call: **`needs_review`, reason `too_long`** (a stronger model would be cut off the same way) |
| `InvalidOutput` (not valid against the schema, rare with structured outputs) | once more on the same rung; then escalate |
| `Refused` | `needs_review`, reason `refused`; the same input is not sent again (ADR-0011). Billed |
| `ModelUnavailable` | skip this rung, remember it, continue at the next |
| `KeyProblem` (rejected, billing, monthly cap, the owner's own limit) | **stop the whole document**, keep what is read, end the job as provider-unavailable with the long delay of ADR-0011. No escalation can help |
| `Unavailable`, `Timeout` | stop at this page; the job retries later (no attempt used for the first, one for the second) and **resumes at this page and rung** |
| `Rejected` (our request was wrong) | `needs_review`, reason `request_rejected`: a bug, and it is logged with the request id |
| `CannotBeSentSafely` (strict redaction) | `needs_review`, reason `cannot_be_sent_safely`; nothing was sent |

## 6. Budgets and caps: the loop cannot run away
Two kinds of limit, both checked by the state machine **before** a call, so a call that would break one does not happen:
- **Caps independent of money** (ADR-0011): at most **5 calls per page** (one per rung plus a retry) and **3 calls per page of the document plus 10** per document. They bound the damage of a bug in the rules, whatever the prices are.
- **Money:** the next call may happen only if `spent so far + the worst case of that call <= the document cap`, and `+ ... <= what is left of the month`. The worst case is the estimated input plus the rung's **largest answer** at its output price; token counting is free, so the input is exact for a real page. Reserving the worst case is stricter than needed (most answers are a tenth of the cap) and is what makes the promise of ADR-0011 true: a call that would breach a budget does not happen. When the check fails the page ends `needs_review`, reason `budget`, and the job says whether it was the document or the month.

At the defaults (R5 a document, R100 a month, ADR-0011) the output part of the worst case of one call, the answer cap times the output price at R18/USD, is about R0.14 on Haiku, R2.2 on Sonnet, R2.9 on Opus and R3.6 on Fable. Adding the input of a page (about 6 000 tokens, R0.01 to R1.1 depending on the model) every rung still fits in a document cap of R5, and that is why the caps in §2 are what they are. Fable only just fits, which is another reason it is off by default.

**A flat R5 stops long documents.** A 300-page statement read once at Haiku costs about R6 before any escalation. I propose the document cap **grows with the pages**: the larger of the configured amount and R0.50 a page, still never above the month's remaining budget. Question 6.

The monthly budget table, the tenant settings (Fable on or off) and the batch mode are P2-12. The router asks a small `SpendGate` (reserve, then record the real usage) so P2-12 can plug in; until then the gate is the per-document one, kept in memory, and **nothing may run against a real key until P2-12 is built** (the handler is not wired into the server yet, so this costs nothing now).

**Illustration, not a measurement.** If 90 pages in 100 pass at Haiku, 8 go on to Sonnet and 2 to Opus, the expected cost is `0.02 + 0.10 x 0.40 + 0.02 x 0.79`, about **R0.08 a page**: R0.80 for a 10-page invoice, R8 for 100 pages. The percentages are guesses; the first gold-set run replaces them. If every page used every rung it would be R3.19 a page, which is exactly what the budget exists to stop.

## 7. Order, context and the prompt cache
- **Pages are read in order, one at a time (concurrency 1) in this version.** Each page's pack carries what earlier pages established (the currency, the invoice number, the supplier, whether totals were seen, ADR-0014 §1), and the conversion needs `currency_known` from an earlier page. Reading pages in parallel would lose both. It also satisfies the cache rule for free: the first call finishes before the next starts, and each read refreshes the five-minute entry. A 100-page document at about 10 seconds a page is under 20 minutes, which suits a background job. Bounded fan-out is added with the rate-limit-aware client (P2-24), once the gold set shows that context matters less than speed.
- **Escalating pays a new cache write**, because the cache is per model: about 1.25 times the rules prefix once per rung used. It is small, and it is logged.
- **The cache lifetime** is five minutes; one hour for bulk uploads (P2-16).

## 8. What is stored
Two new tables, both under row-level security and erased with the document. **The SQL is shown to Kone before it is applied**, as for every schema change.
- **`page_readings`:** one row per page: the final reading as the model gave it (the `PageReading` JSON), the converted problems, the findings, the rung, the confidence basis and the outcome (`read` or `needs_review` with the fixed reason). It is what a job resumes from, what a reviewer starts with (a page that went to review keeps the **best draft**: the attempt with the fewest blocking issues, the higher rung on a tie), and what the audit of ADR-0004 needs. **It holds invoice content.** The readings of rejected attempts are not kept; only the final one is.
- **`model_calls`:** append-only, **no content at all**: one row per call with the page, attempt, rung, model, effort, picture size, the prompt and shape versions, the pack manifest (ADR-0014: section sizes and counts, never text), the four usage counts, the cost in rand, the time taken, Anthropic's request id, and the outcome (`accepted`, `escalated` with the reason, or the error kind). This is P2-15, and it answers "was context missing?" and "did the cache hit?".
- A `document.read` audit entry with the page counts, the rungs used, the total cost in rand cents and how the document ended (counts and fixed names only).

## 9. How a page ends, and how the document does
`PageOutcome` is `Read { rung, extraction, notes }` or `NeedsReview { reason, draft }`, with `notes` holding what was recorded but did not block (document-level findings, `injection_suspected`, redaction counts). The reasons are a fixed list: `top_rung_failed`, `too_long`, `refused`, `budget`, `call_cap`, `cannot_be_sent_safely`, `request_rejected`, `no_rung_available`. A document with any page in review ends `needs_review` but keeps every page it read, so a person starts from the drafts. Until P2-07 (putting pages together) exists, the handler still ends the job `needs_review` with "read; the later stages are not built yet", the same honest ending ADR-0017 uses, so no document is marked done for work that was not done.

## 10. Tests (no key, no money)
- **The state machine** against scripts: accept first time; escalate on each named reason up the ladder and stop at the top; every error row of §5; truncation retried once; the caps and the budget refuse the call that would break them; a skipped rung; resuming at a rung. A **termination property**: for any generated sequence of outcomes the machine reaches `Done` within `5 x rungs` steps and never exceeds a cap.
- **The assessment** over the 15 synthetic gold-set cases: a correct reading is accepted; each kind of corruption (one digit of a line total, a swapped total, a number not on the page, a bad date) is escalated with the right reason; a corruption that is consistent with the text and the arithmetic is *not* caught, and a test says so (that is the limit of deterministic checking, and what the reviewer is for).
- **Document-level subtleties:** a continuation page with no lines is accepted; a page 3 of 5 whose lines do not match the printed total is **not** escalated; a due date before the invoice date is a note and not a reason.
- **The driver** with `FakeProvider` and `FakeWorker`: the pack that is sent for each route, higher picture size on the upper rungs, the failure report in the second call, no text in any log or `Debug`, a hostile page (injection phrases) changes nothing about the next step, `CannotBeSentSafely` sends nothing.
- **The costs:** every price times every usage kind, rounding up, the 100 000-token step of Haiku, cache reads and the one-hour write.
- **Stored results:** resume after a stop skips finished pages and repeats only the page in progress; erasure takes both tables; a tenant cannot see another's.
- **A live check for the day there is a key** (`#[ignore]`, never run in CI): one real page through the whole path on Haiku, printing the cost in rand; and the gold-set run that finally measures the pass rate per rung, the cost per page and the cache hit rate.
- A hand mutation check, as for every crate.

## Implementation notes

**Step 1, `escalation` in `clearcut-core`** (the rules; no I/O, no money, no model; 80 new tests, 490 in the crate):
1. **`RouterPolicy`** is the ladder as data, checked when built: at least one rung on, plain unique model ids (letters, digits, `-`, `_`, `.`, at most 128), each rung's answer cap between 1 and the ceiling (16 000 by default, at most the provider's 64 000), each rung's picture inside what the worker draws (100 to 300 dpi, 500 to 2 576 pixels), call caps above zero. `default_ladder()` is the table of section 2 (Fable off). `with_enabled` turns a model on or off and checks again, so the last rung that is on cannot be switched off; `without_models` takes out the models a key cannot use and is deliberately not checked (a key may use none, and the router then says `no_rung_available` instead of failing to start). `document_call_cap(pages)` is 3 a page plus 10, saturating. A rung is named by its position in `rungs()`, so the driver must use the policy it started the page with.
2. **`assess`** takes the problems converting the reading, the findings of `validate`, a `TextCheck` (not available, passed, failed with a count) and whether the page is the whole document, and returns a verdict, how many things block, notes, every reason that applies (the first is the one named, in the order reading problems, line arithmetic, totals, text check) and a confidence basis. **A problem on a path nobody listed is critical**, so a new path in the converter can never hide a problem; the non-critical ones are exactly the recipient, the due date, the supplier's address and a credit note's original invoice number. Line arithmetic (a total that is not quantity times price, a zero or negative quantity, an amount out of range, a currency mismatch) escalates on every page; the totals check only on a one-page document; no lines is never a reason; a due date before the invoice date and a tax-invoice rule the document breaks are notes.
3. **Two things the ADR left open, settled here:** (a) `amounts_include_vat` and `too_many_lines` are review verdicts at once, never escalations (a stronger model reads the same printed amounts, and the same long page); `amounts_include_vat` wins over `too_long` whichever comes first, and both count as blocking so the reading can still be the best draft. (b) `ReviewReason` gains `amounts_include_vat` beside the eight of section 9, and `EscalationReason` has the two ADR reasons for same-rung problems as `schema_invalid` and `rung_unavailable`.
4. **`PageReader`** is the state machine: `start(policy, document_calls_left)` and `on_outcome(outcome)` each return a `Step`, a `Call(CallPlan)` (attempt number, rung, model, effort, answer cap, picture and a `CallKind`: first, escalation with the rung it came from and the reason, retry after a cut-off, retry after an invalid answer) or `Done(PageOutcome)`. It counts calls (a call refused before it was sent is not one), keeps the best draft (fewest blocking issues; a tie goes to the later, higher rung; a reading that could not be converted is no draft), retries a cut-off once with the ceiling and an invalid answer once, and gives each new rung its own retries. Once done it keeps saying so. It is `Serialize` and `Deserialize`, so a job taken over mid-page resumes from the stored machine; the stored form holds counters, model ids and fixed names. **Reading either type back goes through the same checks as building it** (`serde(try_from)`; found in the automated security review): a `RouterPolicy` from a configuration file cannot hold what `RouterPolicy::new` would refuse, and a stored `PageReader` that has been damaged or edited is refused (a position outside the rungs, more calls than the limit or than were planned, a raised cap outside 1 to the ceiling, a best attempt that was never planned, a rung no policy could hold), instead of panicking on an index or spending more calls than the page was allowed. A page that is already finished may have no rungs and still reads back.
5. **It always ends.** Tests run every sequence of five outcomes over twelve kinds (248 832 of them) and 20 000 generated policies and outcome streams, and require the page to be done within its cap, never issuing more calls than the page cap or the document's calls left.
6. **Mutation check:** about 145 deliberate breakages of the three files; the survivors of the first run were missing tests (the blocking count of the two review problems and the order in which they come, and the rung a reading is named by when an earlier rung is off) and are caught now. One field turned out to be redundant (a flag saying the cut-off retry had been used, since the raised cap already stops a second one) and was removed rather than tested.
7. **Not done in this step:** prices and cost (step 2), the text check itself (step 3), the pack's `unverified_text_layer` label (step 4), the driver (step 5), the tables (step 6) and the read stage (step 7).

**Step 2, `cost` in `clearcut-core`** (money arithmetic and budgets; pure; 56 new tests, 546 in the crate; the first half of P2-12):
1. **Units.** A cost is a whole number of **nano-rand** (`Cost`, a billionth of a rand): one Haiku token costs under a millionth of a rand, so a cent is far too coarse. Prices are kept in **millionths of a US dollar per million tokens**, so every published price and cache multiple is exact: reads 0.1x (Haiku), 0.05x (Sonnet, Opus), 0.025x (Fable); writes 1.25x for five minutes and 2x for an hour on all four. The cost is `tokens x price x rand cents to the dollar / 100 000` summed over the kinds of token and **rounded up** once (the error is always in the user's favour); a cost is shown and compared in rand cents rounded up (`R0.02`). Everything saturates and none of it uses a float. `ExchangeRate` is in rand cents to the dollar, default 1 800 (R18.00), between R0.01 and R1 000.
2. **`PriceTable`** holds the four models with the date the prices were read (22 October 2026, from research 06; **check them against Anthropic's pricing page before relying on them**). It refuses a price of zero (a budget would call the call free), a duplicate or odd model id, a date that is not `YYYY-MM-DD`, and a long-prompt rate below the standard one. Haiku's higher price applies when the **input side** of a call (input plus both kinds of cache token) is **more than** 100 000 tokens, to every token of that call; this reading of Anthropic's wording is conservative and the live check should confirm it. A model with no price cannot be costed, so it cannot be afforded (`UnknownModelPrice`, and `unaffordable_models` lists it).
3. **`worst_case`** is the page at the input price, the cached prefix at the dearer of the input price and the one-hour write price (it may have to be written), and the rung's largest answer. A real call of that size never costs more (tested over the mixes of cache kinds). `unaffordable_models` lists the rungs that are on whose worst case does not fit a cap; the driver takes them out with `RouterPolicy::without_models`.
   **Found while working it out:** the ADR said every rung fits in R5 and Fable "only just". For a typical page (6 000 tokens after the breakpoint) that holds only if no cache has to be written: Fable is then R4.68. If the 4 000-token prefix has to be written for an hour it is **R6.12**, which does not fit, so Fable would be taken out of the ladder on a document's first call at the default cap (it is off by default, and the cap grows with the pages, R0.50 each, so a document of 13 pages or more has room). Opus is R3.89 in the same case and fits.
4. **`BudgetPolicy` and `BudgetCheck`.** The defaults are R5 a document, R0.50 a page and R100 a month. The document's cap is the **larger** of R5 and R0.50 times its pages (ten pages is exactly R5.00; 300 pages R150); `BudgetCheck::check(worst)` allows a call if the document's spending plus its worst case is within the cap (reaching it exactly is allowed) and the month's spending, counting this document, is within the month; the document is named first when both would be broken. A cap larger than the month never lets a document past the month. `record(actual)` adds what a call really cost, so the estimate is only ever a reservation. The checks are plain data and survive being stored in a checkpoint.
5. **Read-back is checked** (the lesson of the review of step 1): `ExchangeRate`, `PriceTable` and `BudgetPolicy` go through the same checks when read from text as when built.
6. **Mutation check:** about 90 deliberate breakages of the three files (units, each multiple, the long-prompt threshold, rounding up, the clamp on one-hour writes, every validation, the limit edges and the order of the two scopes). The survivors of the first run were missing tests: dates that are wrong in exactly one way, a long-prompt rate that is cheaper in only one direction, and that recording adds. All are caught now.
7. **Not done in this step:** the month's ledger and the tenant settings (the rest of P2-12), the `SpendGate` the router will ask, the text check, the pack label, the driver, the tables and the read stage (steps 3 to 7).

**Step 3, `text_check` in `clearcut-core`** (P2-13c: did the model read what the page says; pure; 31 new tests, 576 in the crate):
1. **What is looked for.** Every amount of the reading that is not zero (each line's unit price and total, the three totals, a credit note's amount), the invoice number and the supplier's VAT number. `check_against_text(extraction, text, trust)` returns a `TextCheckReport`: the `TextCheck` the assessment takes, how many figures were looked for, and the **place** of each one not found (`totals/gross`, `lines/2/line_total`), in a fixed order. It holds no value from the reading or the page (tested).
2. **Amounts.** The text is scanned for runs of digit groups joined by single separators (space, non-breaking space, comma, point, apostrophe, typographic apostrophe), and **every stretch of a run is a reading**: `1 234,50`, `1,234.50`, `1.234,50`, `1'234.50`, `R1234.50`, `1 500`, `12.5`, `0,5` all give their value in cents; a sign or brackets are ignored. The last group is cents when it has one or two digits and follows a point or comma (a space is not a decimal point: `12 50` is not R12.50), or thousands when the groups are a first group of up to three digits and then groups of exactly three. A run is cut at 32 groups, which bounds the work (with the cut removed the test with a page of 100 000 numbers never finishes, which is how the mutation check showed it matters). ASCII digits only.
3. **The invoice number and the VAT number** are found as a whole: lower-cased letters and digits (digits only for the VAT number) must start where a run of such characters starts and be followed by the start of another run or the end, so `INV-000001` is found in `inv 000001` and `INV/000001` but not in `INV-0000011` or `XINV-000001`, and `4123456789` is found as `4123 456 789` but not inside `04123456789`.
4. **Zero is not checked** (a page may print a dash or nothing for VAT). **Dates, quantities, names and descriptions are not**: a small quantity is on every page, and a date is printed in too many forms (and months in two languages) for a miss to mean anything yet; a false failure sends a correct page up the ladder and ends it in review. The gold set will say whether dates are worth adding.
5. **A deliberate departure from the wording of section 3.** The ADR said the check applies to `text_and_image` and `image_first` pages and to OCR text. A miss only counts as a **failure** when the text is `Trusted` (a text layer that passed its checks, route `text_and_image`). When the text is `Unverified` (a layer that OCR only partly agreed with, route `image_first`, or OCR text of a scan) a miss is reported but the result is `NotAvailable`, because the text may be the wrong one: with digits shifted in a lying layer the model that read the picture correctly would otherwise fail every rung and end in review. Agreement is still evidence in either case (two independent readers saw the same figures, `Passed`). Nothing to check, or no usable text, is `NotAvailable`, never `Passed`.
6. **Known limit, on purpose:** a space is a thousands separator in South Africa and also separates neighbouring numbers, so `10 150.00` is also R10 150.00 and a model that merged two neighbours is confirmed. The check is evidence, not proof; the arithmetic is what catches that. A test states it.
7. **Mutation check:** about 80 deliberate breakages (each separator, each form of grouping, the cents rules, the word boundaries, the zero rule, the trust rule, the order of the places). Survivors of the first run were missing tests, and four pieces of code turned out to be implied by others (a 15-digit guard the checked arithmetic already makes unnecessary, a `len == 3` beside a grouping check, the lower bound of the first group, a flag that only an empty group could trip) and were removed instead of tested. The two mutants that remove the cap on a run hang the page-of-numbers test, which counts as caught; the mutation harness now has a per-mutant time limit.
8. **Not done:** the locator (`TextSpan`) of ADR-0013 section 4 is not derived yet; the match positions are there to do it, and it waits for the citation work (P3-08). The pack label (step 4), the driver (step 5), the tables (step 6) and the read stage (step 7) follow.

**Step 4, the text label in the context pack** (`clearcut-pack` and a line in `clearcut-docproc`; 16 new tests in the pack, 1 in docproc; 64 and 143 in all):
1. **`TextSource::UnverifiedTextLayer`** (`unverified_text_layer`) joins `text_layer` and `ocr`. It labels the document's own text layer when it could not be checked (route `image_first`): in the tag of the page text (`<page_text id="..." source="unverified_text_layer">`) and in the manifest's `text_source`. Its own text is redacted like any other text. **It cannot vouch for the picture** (found in the automated security review): the layer may say something other than what is printed, so a search of it finding nothing proves nothing about the image, and painting from its words could miss data that is really there. So a page with an image and an unverified layer has image state `unchecked`: the picture goes as it is (the policy `best_effort` records that), the masker is not asked, and under `strict` the page is refused (`cannot_be_sent_safely`, `NothingToCheck`) and goes to a person. The cost is that under `strict` every `image_first` page goes to review; the better answer is to redact and mask such a page from its **OCR** text and words (OCR reads the picture itself, and the analysis already runs OCR on every page that is not `Good` when the worker has it), which is left as a follow-up for when the gold set shows how many pages that is.
2. **`PageText::for_route(route, source, content)`** is the one place that decides what text goes with a page and how it is labelled: a checked layer for `text_and_image`, an unchecked one for `image_first`, OCR text for `image_only`. A page with no text, text that is only white space, and any combination a reading cannot produce (a rejected layer on an `image_only` page, OCR text on a `text_and_image` page) is **no text**, so a rejected text layer can never be sent by mistake.
3. **One sentence is added to the cached rules** (`prompt-v1/rules.md`), naming the four labels and what each means for the model: a checked layer is usually reliable; OCR can make mistakes; an unverified layer may be wrong, so the picture is the only source for what is printed and the text is only a hint for reading unclear characters; `none` means read the image. As ADR-0014 did before, **`prompt-v1` is edited in place and its golden file regenerated** (one added line), because no live call has ever been made; the first live call is what freezes it. The cached prefix stays identical whatever the source of a page's text (tested), so the cache is not affected by which label a page has.
4. **The worker's masker** (`WorkerMasker`) refuses an unverified text layer for any page (`MaskError::Failed`, nothing asked of the worker): its words are not a basis for painting. (It briefly accepted one for a PDF-text page; the review above is why it does not.)
5. **Mutation check:** 26 deliberate breakages (every arm of the route mapping and the wildcard, the white-space rule, each label, the masker's pairs, every clause of the new rules text, which the tests read, and each part of the fail-closed rule for the picture): all caught.
6. **Not done:** the driver that builds each page's pack from a stored reading (step 5), the tables (step 6) and the read stage (step 7).

**Step 5, the driver** (the new crate `clearcut-router`; 68 tests there, plus 7 in `clearcut-core` for what the driver needed of the state machine: 583 in all):
1. **Shape.** `Router<P: ModelProvider, W: DocumentProcessor>` with a `RouterConfig` (policy, prices, exchange rate, output schema, cache lifetime, redaction policy, tenant rules) and one method, `read_page(task, budget, document_calls_left, resume)`. A `PageTask` holds the page, its route and text source from the analysis, what earlier pages established and a currency known from another page. The result is `PageRun::Finished(PageResult)` or `PageRun::Interrupted(Interruption)`. The crate has no database: the caller keeps the money ledger and stores what comes back (step 7).
2. **One call, in order.** The text the route calls for (a checked layer with word boxes; a hint layer without; OCR for a scan; nothing for a page with none) is fetched **once per run**, the picture is drawn **once per size** (Haiku and Sonnet share one, Opus draws its own), personal data in the picture is painted over by `WorkerMasker` from the same redaction the pack computes, the pack is built, the **worst case of the call is checked against the budget**, the provider is called, and the answer is converted, validated, checked against the page's text and assessed. The state machine hears only the outcome. Nothing is fetched until the first call is due, so a page with no calls left touches nothing.
3. **Failures of the service stop the page and use up nothing.** A provider that is down or throttling, a timeout, a bad or exhausted key, and a worker that cannot give the text or the picture all return `Interrupted` with a `Carry`: the state machine (which now remembers **the call it was about to make**, `PageReader::pending`, validated when read back) and the readings kept so far. Resuming with the carry makes the very same call again. The carry is checked when read back (`try_from`): attempts that do not match the machine, a best reading that is not the machine's best, a reading that is not a reading, or one from a call not yet made are refused (the lesson of #62).
4. **What the next model is told.** The failed reading is re-evaluated (so it survives a resume, where only the reading itself is stored) and reported in ClearCut's words: what could not be read exactly; which figures the page does not show, **only where the text can be believed** (a trusted layer; against an unverified one the misses are recorded in the result but not blamed on the model); and the checks that stopped the reading (line arithmetic, and the totals only on a one-page document). Tax-invoice findings and a due date before the invoice date are facts about the document that no model could change; they are left out so that a model is not invited to invent a fix. `NotOnPage` is a new problem kind for this, never produced by the conversion.
5. **Money.** The estimate is deliberately high (our own text at three bytes to a token, **the document's text at a token a byte** because digits, symbols and non-Latin text can cost that much and the page is the document's to write, the schema counted on every call, a picture by its 28 by 28 patches up to 4 784, the cached prefix at the dearer of its input and one-hour write price). A model with no price is never called (`BudgetStop::NoPrice`). Every billed call, including a refusal, a cut-off and an answer that was not the shape, is charged what it was billed to the budget and to the result. An unavailable model costs nothing and is remembered for the rest of the document. **A failure after the request was sent is charged at the worst case of the call**, because it may have been processed and the provider cannot say: a timeout, a connection cut part-way (the adapter now reports it as `Timeout`, no longer as `Unavailable`, and no longer retries it inline where the budget cannot see the second bill), and a billed failure that reports no tokens (an answer too large to read). A refusal before any work (overloaded, bad key, billing, nothing reached) is not billed. (Both found in the automated security review of the PR: a three-byte estimate could be under-reserved by a page of dense text, and a loop of timeouts could spend past the cap unseen.)
6. **Pack failures.** `CannotBeSentSafely` (strict policy) ends the page in review with nothing sent and a call record that says so. A page whose text is larger than the pack ever sends is read from its picture alone (never cut). Any other pack error is our bug and is `RequestRejected`.
7. **The call log holds no content.** A `CallRecord` has the attempt, rung, model, effort, picture size, kind, prompt version, the pack's manifest (sizes, hashes, counts), tokens, rand, time, the provider's request id and a fixed label (`accepted`, `escalated(reason)`, `reviewed(reason)`, `invalid_output`, `truncated`, `refused`, `rejected`, `rung_unavailable`, `not_sent(reason)`, `interrupted(kind)`). The reading and the extraction are the one place the page's content goes. The confidence stamped on the values is the evidence of the final verdict (`950` / `850` / `500`), so each value is converted twice: once to decide, once to stamp.
8. **Small decisions.** The extractor's name is the model name the provider answered with (the asked one if it left it out). The check against the text uses the page's **own** text, not the redacted copy that was sent. The picture is not kept across a resume (it is drawn again; one extra render after a rare outage).
9. **Mutation check:** 49 deliberate breakages in the driver and its estimate. The first run left 22 alive: most were missing tests (the call context, effort, cache lifetime and tenant rules reaching the request; the review label; each check of the stored carry; the report's treatment of unverified text; an OCR answer that is not OCR) and are caught now. Two pieces of code were implied by others and were simplified instead of tested (the driver's own guard against painting from an unverified layer, which `WorkerMasker` already refuses; a duplicate check on unavailable models, which a rung left behind cannot repeat), and the text-size sum moved to `estimate.rs` where it has its own test. **Three survivors are equivalent:** an accepted page's reading is both the last and the best (the machine breaks ties toward the later attempt, and an accepted reading has no blocking issue), the draft lookup finds the best first, and the fallback that charges a call its worst case when its model has no price cannot be reached (the price was checked before the call).
10. **Not done:** the tables for the readings and the call log (step 6), the stage that runs this over a document's pages, keeps the money ledger and resumes (step 7), the month ledger and tenant settings (rest of P2-12), and a live test (step 8). Pages are read one after the other (concurrency 1), as decided.

**Step 6, the tables and the store functions** (migration `0007_page_readings_model_calls.sql`, shown to Kone first and approved; `clearcut-store` 163 to 209 tests, `clearcut-core` 583 to 587):
1. **`page_readings`** (one row per page, under row-level security, erased with the document): a `state` of `in_progress`, `read` or `needs_review`. An `in_progress` row holds the router's **carry** (opaque JSON to the store; the checkpoint of a job is limited to 64 KiB and a carry can hold two readings, so it has its own column); an ended row holds the reading that counts (rung, attempt, evidence, model, the reading as JSON) or, for a page sent to a person, the best draft or none, with the fixed review reason, the problems, the findings (which carry amounts), the notes, the places the page's text did not confirm and the kinds of instruction-like text found. The table's `check` makes the three shapes the only ones that can be stored (a page that was read has evidence and no reason; a draft is `unresolved`; a carry exists only while in progress). The application role may `update` it (the first table where it may): derived data, like `page_reads`.
2. **A page that ended is final.** `save_page_reading` is an upsert that only replaces a row that is still `in_progress` (`PageReadingFinished` otherwise), so a stale writer (a job that was taken over) cannot put a carry back over a result; a re-run calls `delete_page_readings` first. The store checks each state's shape and sizes in Rust before the database does (clear messages; the table's checks remain a second line) and checks every row again as it reads it.
3. **`model_calls`** (append-only, no content): attempt, rung, model, effort, picture size, kind (with origin and reason for an escalation), prompt version, the pack's manifest, the five token counts, **the cost charged in nano-rand**, time, request id and a fixed label with a detail. It is append-only for everyone including the owner and has **no erasure escape hatch** (the audit log's trigger function), **no foreign key to the document** and no privilege for the eraser, so erasing a document keeps what it cost; the month's spending (`spend_since`, with the month boundary left to the caller) is added up from it. A count too large for its column is stored at the column's largest (never wrapped), and a sum too large for a cost is the largest cost. A call can be recorded for a document that has since been erased.
4. **One change to the approved SQL**, found by a test: the check tying an escalation to its origin and reason let a `first` call carry one of the two on its own. It is now `(kind = escalation) = (reason is not null)` and `(kind = escalation) = (origin is not null)`.
5. **The table's size limits count the stored (binary) form**, which is larger than the JSON text (a number is a number of its own, not a character), so the Rust limits leave room (250 000 bytes for a reading or carry, 60 000 for a list, 15 000 for a manifest). A number-heavy list that fits as text but not in the table is refused with a clear error, not a database error.
6. **Names in `clearcut-core`:** `ReviewReason::parse`, `ConfidenceBasis::as_str` / `parse` and `ThinkingEffort::as_str`, the fixed names stored in these tables.
7. **Mutation check:** 58 deliberate breakages in the two modules (every bound of every limit, each kind's name, the final-page rule, the inclusive start of a spend, the saturation of counts and sums, each stored-row check). The first run left 11 alive; all were missing boundary tests or stored-row tests, now caught. **One survivor is equivalent:** the `order by page` of the load, because Postgres returns the rows in primary-key order anyway; it stays because the order is a promise of the function.
8. **Not done:** the read stage that uses these (step 7), the month boundary and the ledger around `spend_since` (rest of P2-12), a way to read the call log back (P2-15 proper, for review and the dashboard), and a mapping of the router's `CallLabel` and `Interruption` to these rows (it belongs to the stage).

**Step 7, the read stage** (`clearcut-pipeline`: `read.rs`, `call_log.rs`, `month.rs`; the pipeline goes from 34 to 81 tests, the router from 67 to 71, the store from 209 to 212):
1. **Wiring.** `PipelineHandler::with_models(provider, ReadSettings)` turns the stage on; without it the handler is exactly what it was (analysis, then `needs_review` with `AFTER_ANALYSIS`) and no model can be asked (`NoModel` cannot be built). `ReadSettings` holds the router's configuration, the budget policy (default R5 a document, R0.50 a page, R100 a month) and the time zone of the month (default South Africa, UTC+2). It is the operator's setting; per-tenant settings (Fable on or off, redaction policy) are P2-12. The server does not use it yet (P1-07). **Nothing may run against a real key until the monthly ledger and the spend gate of P2-12 exist.**
2. **The loop.** Pages are read in order, one at a time. A page that ended in an earlier run is skipped (and what it established is replayed from its stored reading, so a resumed job knows the currency, the invoice number, the supplier, whether totals were seen and how many lines earlier pages had); a page stopped midway resumes from its stored carry (a carry that no longer passes its checks means the page is read again from the start); every other page goes to the router. **Only a page that was read teaches the next one**: a draft from a page that went to a person is not offered as fact.
3. **Money comes from the call log, so it survives a restart.** At the start of the stage the budget is rebuilt: the tenant's spending since the start of the calendar month (in the configured time zone, `month_start`) less this document's own spending (which the check adds back as the document's), and the document's calls so far against its allowance (3 a page plus 10). Calls are logged **before** the page is stored, so a failure of the second leaves the first on the books. A page whose service failed stops the job with the fixed kind the router gave (a timeout counts against the attempts; a provider that is down or a key problem does not) and its carry is stored; the call that failed is logged, charged at its worst case if it was a timeout.
4. **A model the key cannot use** is remembered for the rest of the document (the next page does not try it again). The ADR's hour-long memory per tenant is not built.
5. **The end.** When every page has ended the stage writes a `document.read` audit entry (counts and fixed names only: pages, read, in review, the reasons, calls, cost in rand cents rounded up, the pages read per rung) and the checkpoint `{stage: read}` so a taken-over job neither repeats the audit nor redoes anything. The job still ends `needs_review`, honestly: `read; the later stages are not built yet`, or `N of M pages need review; ...`. If the pages in the database are not all there at the end (someone erased rows while the job ran) the job fails as transient and is not called finished.
6. **Supporting changes.** The router reports where a reading came from (`PageResult::reading_from`: rung, attempt, model), which a draft read in an earlier run needs; a kept reading carries its rung. The store gains `document_spend` (what one document has cost and how many allowed calls it has used, read from the log, still there after erasure). `CallLabel` maps to the log's fixed names in `call_log.rs`.
7. **Mutation check:** 54 deliberate breakages of the stage, the handler and the store function. The first run left 12 alive; five were missing tests (a draft's note and rung, the job id in the request, the document's own spending counted once against the month, a page read before a crash with no currency of its own, the guard against pages that vanish), five were code the loop made unnecessary (an `already_read` shortcut, the count of finished pages and its check) and were removed, and one did not compile. **Two survivors are equivalent:** the currency learned from a page is the one already known (a page with another currency cannot be converted), and a saturating count of calls (it would take four billion rows).
8. **Known limits, to be closed by later work:** (a) two documents running at once do not see each other's spending until it is logged (`SpendGate`, P2-12); (b) the calls of a page whose job dies in the middle of it are not logged (a hook per call in the router would close that); (c) the job queue's `Failure` has no delay, so the long wait ADR-0011 wants after a monthly spend cap is not honoured; the job is retried at the queue's usual pace and does not use up attempts; (d) once the budget is spent every remaining page is still fetched and refused one by one instead of the stage stopping at once; (e) a model whose worst call cannot fit the document's cap is refused on each page, not taken out of the ladder up front (`unaffordable_models` is not used); (f) the whole file is read again from storage on a resume, even if nothing is left to read.
9. **Not done:** step 8 (the `#[ignore]`d live test and the final docs), the month ledger and tenant settings (rest of P2-12), putting the pages together (P2-07), and wiring the handler into the server (P1-07).

## Build order (after approval)
1. `escalation` in `clearcut-core`: the policy, the assessment, the state machine, confidence from evidence. 2. `cost` in core (prices and `Cost`; the first half of P2-12). 3. The text check against the page's own text (P2-13c). 4. The pack: the `unverified_text_layer` label and the rules sentence. 5. The `clearcut-router` crate (the driver, with the fakes). 6. The migration for `page_readings` and `model_calls` (shown first) and the store functions. 7. The read stage in `clearcut-pipeline`, resuming. 8. Mutation check, live-test stub, docs.

## Alternatives considered
- *Start scans and doubtful pages at Sonnet* (ADR-0005). See §4: a failed cheap attempt costs two cents.
- *Ask the model how sure it is, and escalate on low confidence.* Not calibrated, and invisible to the checks; replaced by evidence.
- *Always read twice and compare.* Doubles the bill on every page to catch what arithmetic and the text check already catch.
- *Escalate the whole document, not the page.* Pays the top rung for the pages that were fine.
- *Let tools validate inside the model call.* Decided against in ADR-0014 (a loop, an action path from page text); unchanged.
- *The router inside `clearcut-pipeline`.* It would tie the rules to the database and make the loop harder to test; the split in §1 keeps the pure part pure.
- *Retry transport failures in the router.* Multiplies the adapter's and the queue's retries; refused in §5.
- *Read pages in parallel from the start.* Loses context between pages, and needs the rate-limit-aware client first.
