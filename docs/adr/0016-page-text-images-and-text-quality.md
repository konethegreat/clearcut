# ADR-0016: Page text, page images and text quality

Status: **Accepted** (approved by Kone Tshivhinda, 2026-10-23, with all seven recommended answers below) · Date: 2026-10-23 · Deciders: Kone Tshivhinda, Claude
Task P2-05, with the **detection half of P2-20** (glyph-scrambled PDFs) and the worker half of the image masker promised in [ADR-0014](0014-context-pack-builder.md). Builds on [ADR-0009](0009-worker-and-provider-boundary.md) (what the worker is and is not), [ADR-0014](0014-context-pack-builder.md) (what a pack needs per page), [ADR-0013](0013-model-facing-reading-shape.md), and [research 06](../research/06-anthropic-api.md) §7 (images). Licences were read on PyPI and the projects' pages on 23 Oct 2026. Design only; nothing is built until this is approved. P2-20 asks for a spike on real samples before its design is fixed: this ADR fixes only how a bad text layer is **noticed**, with thresholds marked provisional until real samples exist.

## What it is
Today the worker answers one question: how many pages, and which have any text. The context pack (ADR-0014) needs, for each page, a **picture**, the **text** with a note of where it came from, and (for hiding personal data in the picture) **where each word is**. And the whole pipeline needs to know when a text layer **lies**: a PDF whose fonts scramble the glyph-to-character mapping has a text layer that exists and is gibberish, so "has a text layer" is not good enough.

```text
file ─► worker (hostile input, no keys, no internet) ─► facts: text, word boxes, picture, font facts, OCR
                                                        └─► Rust core decides: is this text good? (text_quality)
```

The rule that shapes the design: **the worker reports facts and does pixel and text work; `clearcut-core` decides what they mean.** Thresholds are business rules, they will be tuned on the gold set, and they should not need a Python release to change.

## 1. Libraries, and a correction to ADR-0009
ADR-0009 named PyMuPDF. **PyMuPDF is AGPL-3.0 (or a paid commercial licence)**; an AGPL dependency would make every deployment of ClearCut subject to it and is not acceptable for an Apache-2.0 project meant to be freely used. It is replaced. The rule from now on: **permissive licences only (Apache-2.0, BSD, MIT, HPND); no GPL, LGPL-linked or AGPL code in the worker image**, checked in CI.

| Job | Library | Licence | Notes |
|---|---|---|---|
| Page count, encryption, fonts of a page | **pypdf** (already used) | BSD-3 | Pure Python, so the part that decides "is this document safe to open" is memory-safe |
| Text with character boxes, rendering | **pypdfium2** (PDFium) | BSD-3-Clause / Apache-2.0, plus the licences of what PDFium bundles | PDFium is Chrome's PDF engine; native code, so it only ever runs in the isolated child (§5). The standard wheels are built without the JavaScript engine (to be confirmed when pinning) |
| Resize, PNG/JPEG, strip metadata | **Pillow** | HPND | Decompression-bomb limit set explicitly |
| OCR | **Tesseract** (the program), with the `eng` and `afr` language data | Apache-2.0 (Leptonica: BSD-2) | Run as a program with fixed arguments, not through a wrapper library; **Afrikaans is included because South African documents often are, or are bilingual** |
| Test fixtures only | **reportlab** (BSD), **fontTools** (MIT) | | Make PDFs with known, deliberately scrambled fonts at test time |

Rejected: **PyMuPDF** (AGPL), **Ghostscript** (AGPL) and anything that needs it (OCRmyPDF's PDF paths), **poppler/pdftotext** (GPL), `pytesseract` (a thin wrapper around the same program; one more dependency for no gain), heavy neural OCR (EasyOCR, PaddleOCR, docTR) and Docling for now (large images; an option if Tesseract proves too weak on the gold set). `pdfminer.six` (MIT) is kept in reserve for font analysis if pypdf's view of fonts is not enough.

## 2. The worker's API (v1 additions)
Same hardening as `/v1/inspect`: bearer token checked before the body is read, size cap as bytes arrive, the file type from the bytes, errors that never repeat the file, one child process per request that is killed on overrun. All additions are **stateless**: the file is sent with each call. That re-sends a few megabytes over the private network per page, and avoids the worker keeping other people's documents between calls. If measurement shows it matters, a short-lived spool can be added later by its own decision.

| Route | Body and query | Answer |
|---|---|---|
| `POST /v1/text` | file; `from`, `to` (at most 50 pages per call); `words=true` for boxes | `200` JSON, one entry per page: `page`, `source` (`text_layer` or `none`), `text`, `width_pt`, `height_pt`, `fonts` (§4), and with `words`, `words: [{start, end, x, y, w, h}]` |
| `POST /v1/ocr` | file; `page` | the same shape with `source: "ocr"`, plus a per-word `confidence` (0 to 1000) |
| `POST /v1/render` | file; `page`; `dpi` (100 to 300, default 150); `format` (`png` default) | the image bytes (`image/png` or `image/jpeg`), with `X-Image-Width` and `X-Image-Height` |
| `POST /v1/mask` | a PNG; `boxes` (up to 500) | the PNG with those boxes painted solid black |
| `POST /v1/inspect` | file | now also accepts PNG and JPEG (a phone photo of an invoice is a one-page document) |

- **Boxes** are in **per-mille of the page's width and height**, top-left origin, the same as `Locator::BoundingBox`, so they survive re-rendering at any size. `start` and `end` are **UTF-8 byte offsets into `text`**, the same unit the redaction spans use, so Rust can turn a redaction span into boxes without converting anything (tests check this with accented text and an emoji).
- **`/v1/mask` has no rules in it:** Rust decided which words to hide and sends the rectangles; the worker only paints. This is the real `ImageMasker` ADR-0014 waited for.
- **Limits:** 500 pages (existing), one page's text at most 1 MiB, a page larger than 14 400 points on a side or more than 40 million pixels at the asked-for dpi is refused before rendering, an image document over 40 million pixels is refused before it is decoded.

## 3. Page images (what the model sees)
- **Defaults:** 150 dpi, so an A4 page is about 1 240 x 1 754 px, roughly **2 800 tokens** (research 06 §7). PNG, because lossy compression hurts small print. If the PNG is over **5 MiB** (our own cap, below the API's 10 MB) it is re-encoded as JPEG at quality 90, and only if still too big is it scaled down. The long edge never exceeds **2 000 px** by default (the API takes up to 2 576 on the models we use); a caller can ask for more dpi for a dense scan, within the limits above.
- **Metadata is dropped:** the image is always re-encoded, so EXIF (GPS position, camera, time) from a phone photo never leaves.
- **Orientation:** a photo is rotated upright from its EXIF orientation before the metadata is dropped. Detecting a sideways scan is not attempted here.
- Fonts that PDFium cannot find are substituted, which can change the look but not the content of the page.

## 4. Telling that a text layer lies (the detection half of P2-20)
Two kinds of evidence, one from each side of the boundary.

**Facts the worker reports** (cheap, structural; from pypdf on the page's resources):
- per font used on the page: `kind` (`type1`, `truetype`, `type0`, `type3`, `other`), `has_to_unicode`, `encoding` (`winansi`, `macroman`, `standard`, `identity`, `custom`, `none`), `embedded`;
- on request, an **OCR agreement**: render the page, OCR it, and report the share (per-mille) of the text layer's alphanumeric tokens that also appear in the OCR output. This is the only check that also catches **digits that are permuted but still look like digits**, which no look at the text alone can.

**What Rust computes from the text itself** (pure, in a new `clearcut_core::text_quality`, with fixtures): the share of replacement, private-use and control characters; the share of letters, digits and punctuation; the share of words of three or more letters with **no vowel**; unlikely mid-word capitals; very long unbroken tokens; and **invoice keyword hits** from a short English and Afrikaans list (invoice, tax, vat, total, date, amount, quantity, price, description, due; faktuur, btw, totaal, datum, bedrag, hoeveelheid, prys, beskrywing, vervaldatum). The list is a rule, so it lives in core.

**The verdict** (`Good`, `NeedsCheck`, `Unusable`) comes from core, with provisional thresholds:
- `Unusable`: no text at all; or 5% or more replacement or private-use characters; or an OCR agreement below 50%.
- `NeedsCheck`: a risky font (Type 3, or a font with a custom or identity encoding and no Unicode map) **and** weak text (no keywords, or many vowelless words); or an OCR agreement from 50% to 85%.
- `Good`: otherwise, and also an OCR agreement of 85% or more.

**What each verdict does:**
- `Good`: the text layer goes in the pack as `text_layer`.
- `NeedsCheck`: run the OCR agreement check, which makes it `Good` or `Unusable`.
- `Unusable`: **the text layer is not used**; the page's **OCR text** goes in the pack as `ocr` (so the model still gets text, the redaction rules still have text to check, and the masker still has boxes), and the page is recorded as `text_layer_rejected`.
- **Page 1 of every PDF always gets the OCR agreement check**, as a cheap sentinel for a scrambled document; whether every page should is a question for the gold set.

**What this deliberately does not claim.** Detection reports evidence, not certainty. A scrambled font that maps letters to other letters is usually caught; one that only permutes digits looks like valid text. The defence is the layering that already exists: the model reads the **image**, ADR-0014's rules tell it to trust the image over the text, `validate` re-derives every total to the cent, and the cross-check of P2-13c confirms that the amounts the model read appear in the text layer (a scrambled layer then **disagrees** and the page goes to review). Nothing in this ADR reconstructs a scrambled font's glyph map (P2-20 step 3); that waits for real samples.

## 5. Isolation
The existing child-process design (spawned fresh interpreter, hard time limit with a grace period, crashes stay in the child, answers checked, nothing unpickled) stays. What changes:
- **Bigger answers.** A page's text or image is megabytes, not 256 bytes. The child writes its answer to a file in a **per-request temporary directory** (deleted afterwards) and sends the parent only a small status message; the parent reads the file with a hard size cap. JSON is parsed with a size and depth limit; image bytes are only length-checked and given the right magic bytes, never parsed by the parent.
- **Limits inside the child** on Linux, before it touches the file: `RLIMIT_AS` (address space, 2 GiB by default), `RLIMIT_CPU`, `RLIMIT_NOFILE`, no core dumps. The container supplies the rest (P1-07): non-root user, read-only root file system, no network, no credentials.
- **Tesseract** is run from the child as a program with a fixed list of arguments (no shell), the page image on its input, the result read from its output, a time limit of its own, an empty environment apart from the language-data path, and the temporary directory as its working directory.
- A **parser disagreement is a refusal:** pypdf and PDFium must report the same page count, else the document is `Unreadable`.
- Windows development: the resource limits and OCR tests are skipped when the platform cannot do them; CI on Linux runs them all.

## 6. The Rust side
- `clearcut-docproc`: `DocumentProcessor` gains `page_texts`, `ocr_page`, `render_page` and `mask_image`; new types `PageContent`, `Word`, `FontFacts`, `RenderedPage`; `HttpWorker` and `FakeWorker` follow, with the same error mapping to job failure kinds. A `WorkerMasker` implements ADR-0014's `ImageMasker` by turning redaction spans into boxes through the words and calling `mask_image`.
- `clearcut-core`: `text_quality` (measures, verdict, reasons as fixed words; no text in any reason).
- The pack builder is unchanged: it already takes `PageText { source, content }` and an `ImageMasker`.

## 7. Tests (no key, no real invoice)
- **Generated at test time:** a normal text PDF; a scan (text drawn as an image only); a PDF whose font is a subset with a **custom encoding and no Unicode map**; one with a **Type 3** font; one that **permutes digits only**; a page with accented text and an emoji (for the byte offsets); an encrypted PDF; a tiny page; a huge page (refused); a decompression-bomb PNG (refused); a PNG with EXIF (stripped).
- The 15 synthetic gold-set PDFs: `/v1/text` finds each label's invoice number, date and amounts on the labelled page, and the whole set is `Good`.
- Boxes: for every sample word, the box lies inside the page, and masking a box makes those pixels black and leaves a neighbouring region unchanged.
- The text-quality measures and verdicts have unit tests in core with the generated texts as fixtures; thresholds are constants with a comment saying they are provisional.
- Hostile input: truncated, wrong-type and oversized files; a child that hangs, crashes or answers with oversized or malformed data; errors that never contain file content.
- OCR tests need Tesseract (`eng`, `afr`): the CI job installs it; locally they are skipped when it is absent.
- CI also checks the worker's **dependency licences** against an allowlist, so an AGPL or GPL package cannot slip in.

## Implementation notes

**Step 1a, the licence check** (PR #47): `services/worker/tools/licences.py` and `licence-exceptions.toml`, run by a CI step and by the tests. It reads each installed package's own statement of its licence, follows only the packages in `requirements.txt` and what they need, and accepts only a short permissive allowlist; GPL, LGPL, AGPL, MPL, unknown and unreadable licences are refused. An exception needs the exact wording and a reason, stops working if the wording changes, and is reported once the package is no longer shipped.

**Step 1b, the isolation changes:**
1. **Differs from section 5: the child's answer still travels over the pipe, not through a file.** The pipe carries a message of any size up to a cap the parent chooses (`recv_bytes(max)`), needs no file name the child could point somewhere else (a symlink, a hard link, a named pipe), and is simpler. The per-request scratch directory is kept, for the programs that need one (PDFium temporary files and Tesseract later), and is deleted afterwards, also when the child is killed.
2. `run_in_child(target, args, timeout, max_answer_bytes, limits, ...)` is the one harness; `inspect_isolated` is now a thin use of it with the old 256-byte answer cap. Existing behaviour and tests are unchanged.
3. Before the child touches the file it: makes the module path absolute (a relative entry would stop working after the move), removes what is left of the environment again to an allowlist, moves into the scratch directory and points `TMPDIR`, `TEMP` and `TMP` at it, and applies its limits. Any failure here ends the child silently with no answer, so the parent reports an unreadable document and nothing about the file is printed.
   **The environment is scrubbed when the child is created, not only afterwards** (found in the automated security review of the PR): a program keeps the environment block it was started with, readable from `/proc/self/environ` on Linux, whatever it later removes from `os.environ`, so a parser that has been taken over would still find the bearer token. While a child is being started, under a lock, the worker's own variables outside the allowlist are set aside and put back straight afterwards (also if starting fails). A Linux test reads `/proc/self/environ` in the child; it fails without this and passes with it.
4. **Limits** (`limits.py`): address space 2 GiB, processor time (never more than the parent will wait, rounded up, plus one second), 64 open files, 256 MiB for any file written, no core dumps. A limit is never raised above what the system allows. Platforms without `resource` (Windows) set none; a platform that does not support one limit (macOS has no address-space limit) skips that one; a limit that should be set and cannot be is an error. The limits are tested with a stand-in `resource` module on every platform, and for real (a 2 GiB allocation under a 512 MiB limit, a loop under a 1 s processor limit) on Linux, where they run in CI and were also run in Python 3.12 and 3.14 containers.
   **The deadline covers the whole answer** (found in a second automated review): waiting for the first byte is not a deadline, because a child that has been taken over can start a message and never finish it, which would block the parent for ever. The read happens in a helper thread that the parent waits for with a time limit (timeout plus grace), so whatever happens to the pipe the parent is never stuck in it; at the deadline the child is stopped and the call fails as `TooSlow`. A Linux test sends the start of a message and stalls. **A second review found that killing only the child is not enough:** a taken-over child can leave a helper process holding the pipe open. The child therefore leads its own session and process group (`setsid`), and the parent signals the whole group before it reaps the child (checking that the child still leads the group, so a reused process id cannot hit anyone else). Linux tests: the child leads its group; a grandchild that holds the pipe open is killed and the parent returns at the deadline (both fail without the corresponding code, checked in a container). **A third review found a use-after-close:** the parent used to close its end of the pipe after stopping the child, while a reader thread might still be inside a read on it; the descriptor number could by then belong to another request's pipe. The reader thread now owns its end of the pipe and closes it itself when it is done (a test records who closes each pipe: nobody but the reader may, while it is alive; it fails if the parent closes it again). A helper that has left the group by itself would still hold the pipe; the reader thread then stays blocked (holding that one descriptor) and a warning is logged, and the container's limits (no network, non-root, a process-count limit to be set in P1-07) are what contain it.
5. **Not done in this step:** the check that pypdf and PDFium agree on the page count (PDFium arrives in step 2), system-call filtering, and configuring the limits through settings (the defaults apply until the container work, P1-07).
6. **Mutation check:** the licence tool (20 breakages) and the limits and harness (26 breakages): every one caught except a few equivalent cases (a branch that cannot change an outcome because of what follows it, such as skipping the missing-module check on Windows, or swallowing an error instead of exiting when the parent sees the same silence either way).

**Step 2, `POST /v1/text`:**
1. **Libraries.** pypdfium2 5.14.0 (PDFium) reads the text and the character boxes; pypdf (already shipped) reads the document structure and the fonts. Both are pinned in `constraints.txt`. pypdfium2 states its licence as "BSD-3-Clause, Apache-2.0, dependency licenses", which the allowlist cannot accept as written, so it has one entry in `licence-exceptions.toml` with the reading behind it: the wheels for Windows and Linux (dist-info/licenses) carry the texts of what PDFium bundles (Apache-2.0, BSD-2/3-Clause, MIT, zlib, Unicode-3.0, a permissive notice for Anti-Grain Geometry, and FreeType under its own BSD-style licence, whose credit clause `NOTICE` now meets). The entry stops working if the wording changes.
2. **The answer** is a list of pages: `page`, `source` (`text_layer`, or `none` when a page has no text; then `text` is empty and `fonts` is `[]`), cleaned `text`, `width_pt` and `height_pt` as a reader sees the page (crop box, turned by the rotation), the page's `fonts` (kind, encoding, ToUnicode present, embedded; forms are followed, bounded in depth and number), and with `words=true` the words. A call reads at most 50 pages; leaving `to` out reads to the end but never more than 50. The range is checked against pypdf's page count (`422` with the page count when it runs past the end).
3. **Word offsets and boxes.** PDFium counts in UTF-16 units and the API reports UTF-8 byte offsets into the cleaned text, so `assemble_words` keeps both counts in step (a character outside the basic plane is two units and four bytes; a dropped control character still uses up its place in the engine's numbering). Boxes are in thousandths from the top left of the page as seen and are rounded outwards. **Boxes are PDFium's "loose" character boxes** (the whole line height, ascender to descender) and not the tight box around the ink: the image masker paints over these boxes, and a tight box would leave the descenders of letters like "g" and "y" showing. The price is that boxes of neighbouring lines can touch; a test pins the choice.
4. **The page-count agreement check is done**: if pypdf and PDFium disagree about the number of pages the document is refused as unreadable (a file that two readers see differently is not one to extract from).
5. **Limits.** A page with more than 1 MiB of text or 20 000 words is refused, never cut short (a cut page would look complete). The child's answer may be up to 32 MiB and is decoded field by field by `decode_text_answer`: exact key sets, types (a boolean is not a number), the pages exactly those asked for and in order, no control characters except line feed and tab, consistent `source`, `text` and `fonts`, every word on character boundaries inside the text, in order, without white space, and every box inside the page. Anything else is "unreadable".
6. **Tests.** The test PDFs are generated at test time (`tests/pdfs.py`: pages, fonts, boxes and rotation described in a few lines, with the cross-reference table worked out); no binary fixture is committed. A stand-in PDF engine covers the cases a real one will not produce (a different page count, a character with no box, a slow page, closing).
7. **Mutation check:** 81 breakages of `pagetext.py` and 66 of the answer decoder. The first run let 19 and 21 through; each was a missing test (a named base encoding, the caps on fonts and forms, the deadline between pages, a character the engine cannot measure, a tab or line feed in text, an exact size limit, a negative box position, a boolean page number, and so on), and tests were added until all were caught. The few left are equivalent: a NaN is already refused where it is used, `zip(strict=True)` repeats a length check made one line earlier, and a catch of `BaseException` in the child cannot be reached from a test. One check was dead code (a carriage return is already a control character) and was removed.
8. **Still not done:** the OCR agreement check on page 1 (step 4), system-call filtering, and the Rust client (step 7). The text-quality verdict is not here: this endpoint only reports facts.

**Step 3, `POST /v1/render` and picture documents:**
1. **The call.** `POST /v1/render?page=1&dpi=150&format=png&max_edge=2000`: `dpi` 100 to 300, `format` `png` or `jpeg`, and the answer is the image bytes with `X-Image-Width`, `X-Image-Height` and `Cache-Control: no-store`. **`max_edge` (500 to 2 576) is an addition to the table in section 2**: section 3 says the long side never exceeds 2 000 px by default *and* that a caller can ask for more dpi for a dense scan, which only fits if the cap is itself a parameter. The default is unchanged.
2. **Picture documents.** A PNG or JPEG is a one-page document with no text layer: `/v1/inspect` answers `media_type` `image/png` or `image/jpeg` (the parent's own reading of the bytes it sent, never the child's word), `/v1/text` answers one page with `source: none` measured in pixels (the "points" of a picture are its pixels, after it is turned upright), and `/v1/render` re-encodes it. The Rust client rejects an `image/png` inspect answer until step 7, which is the intended order.
3. **Opening a picture** (`images.py`). Only the PNG and JPEG decoders are enabled (Pillow can read dozens of formats and each is more hostile-input code). The size is read from the header and a picture over 40 million pixels is refused **before anything is decoded** (a test feeds a header that claims 30 000 by 30 000 pixels). EXIF orientation is applied and then dropped, only the first picture of an animated PNG is read, transparent areas become white (not black), and a palette picture with a transparent colour is handled the same way. Exotic modes such as 16-bit grey are not converted and are reported as unreadable; that is a known limit until a real sample needs it.
4. **What leaves is pixels only.** Every picture is decoded to plain RGB and encoded from scratch, so EXIF (position, camera, time), colour profiles and text chunks never leave. Tests look for invented markers in the output bytes and check that a PNG holds only `IHDR`, `IDAT` and `IEND`. PNG first; if over 5 MiB, JPEG at quality 90 with full colour resolution (no 4:2:0, which smears the coloured edges of small print); if still too big the picture is made smaller by steps and refused below a long edge of 100.
5. **Drawing a PDF page** uses PDFium at the dpi asked for, without drawing forms (nothing in an invoice's image needs them, and a form is one more thing that can run). The size is checked before drawing: more than 14 400 points on a side, or more than 40 million pixels at that dpi, is `PageTooBig` (`422`). The two-parser page-count agreement check from step 2 is shared, so the opening code moved into `read_structure` and `open_engine`, and the error classes moved to `errors.py` so `images.py` and `inspect.py` do not import each other.
6. **The child's answer is bytes, not JSON**: a fixed header and then the image, or an error frame with a name from a fixed list. The parent never decodes the picture. It checks the sizes, the opening and closing bytes, and the width and height the picture states for itself: for a PNG, the `IHDR` header; for a JPEG, the frame header, found by a bounded walk over the segment lengths (never into the picture data). A mismatch is "unreadable". The review of the PR that first added the PNG check suggested the JPEG check; it is the same idea.
7. **Pillow 13.0.0** is pinned. Its licence field says `MIT-CMU` (the old HPND text under its SPDX name), which is now on the allowlist. The wheel's licence file was read: it bundles libjpeg-turbo, libpng, zlib-ng, FreeType (`NOTICE` already carries the credit), lcms2, libtiff, libwebp, libavif, openjpeg, brotli, harfbuzz and xz. The only mentions of GPL or LGPL are xz's command-line tools (not in the wheel) and FreeType's alternative GPL option (not used).
8. **Mutation check:** about 125 breakages across `images.py`, `render.py`, the picture code in `isolation.py` and the route in `app.py`. Each survivor was a missing test (the deadline between opening and drawing, passing the pixel limit through, JPEG quality and colour resolution, an answer with a wrong frame name, each branch of the JPEG walk) and tests were added until every one was caught, apart from equivalent cases: a zero-size check that Pillow's own header reading makes unreachable, an explicit decode that the orientation step already forces, a resize to the same size, and a digit check that comes after an ASCII-only decode.
9. **Still not done:** OCR and the OCR agreement (step 4), masking (step 5), `text_quality` (step 6), the Rust client with picture kinds (step 7).

**Step 4, `POST /v1/ocr` and the OCR agreement:**
1. **The call.** `POST /v1/ocr?page=1&agreement=false` answers in the shape of the text answer with one page: `source: "ocr"`, `fonts: []`, every word with its box and a `confidence` from 0 to 1000, and, only when asked, `agreement`. **`agreement` is an addition to the table in section 2**: the agreement needs the page drawn, read by OCR *and* the text layer of the same page, so asking for it on the OCR call costs nothing extra and keeps the worker stateless. OCR is **off unless `CLEARCUT_WORKER_TESSERACT` names the program**: then `/health` lists `ocr`, and without it `/v1/ocr` answers `503 {"error":"OCR is not available"}`. At start the worker asks the program for its languages and **refuses to start** if it cannot be used or lacks English or Afrikaans, so a broken installation is found at once and not at the first scanned page.
2. **Running Tesseract.** One fixed argument list (`page.png result -l eng+afr --oem 1 --psm 3 [--tessdata-dir DIR] tsv`), no shell, in the child's private scratch directory, with no input or output stream, an environment cut down to the allowlist plus one thread and the data directory, and a time limit that is whatever is left of the request's deadline (a program that overruns is stopped and the call is `TooSlow`). The answer is read from the file it writes, after a size check (32 MiB). The page is drawn at 300 dpi for it (long side up to 4 000 px), because small print reads best there; the picture the model is shown stays at 150.
3. **Reading its answer.** The TSV is parsed strictly (exact header, 12 columns, plain ASCII numbers) and every word is cleaned: control characters, noncharacters and any white space are removed, and a word with nothing left is dropped. Words on a line are joined with a space and lines with a line feed; offsets are UTF-8 bytes and boxes are thousandths of the drawn picture, rounded outwards, so they mean the same as the text boxes. Confidence is Tesseract's 0 to 100 times ten, rounded. A page with more than 20 000 words or 1 MiB of text is refused, not cut.
4. **The agreement** is the share, in thousandths and rounded down, of the *distinct* words of two letters or digits or more in the PDF's own text layer (case-folded, split at anything that is not a letter or digit) that OCR also read. It is left out when the page has no text layer or no such words. It is a *fact*: what counts as low is for `clearcut-core` to decide with the other measures in section 4. On generated pages with the real program: an honest page 1000; a page whose visible text says `100.00` and whose invisible text layer says `999.00` 800 (four of its five words were read back); a scan (picture) none. Words of one character are ignored because OCR drops lone glyphs and that would make the number noisy; this threshold is provisional like the others.
5. **Isolation.** OCR runs in the child like everything else; the child's answer is JSON checked field by field (source must be `ocr`, no fonts, a confidence on every word, an agreement exactly when asked, text exactly when there are words).
6. **Tests.** Most run anywhere against a **stand-in program** (a copy of a small script with a scenario beside it; it records the arguments, working directory and environment it was given, which is how the fixed arguments, the scrubbed environment and the scratch directory are tested, and it can fail, hang or write a huge result). Five run against the real program and are skipped where it is not installed: reading a drawn page and where its words are, an honest text layer, a lying one, and a scanned picture with Afrikaans words. CI installs `tesseract-ocr` with the English and Afrikaans data (Tesseract is Apache-2.0, Leptonica BSD-2; they come with the container image, not through pip, so `NOTICE` and the image work (P1-07) carry them).
7. **Mutation check:** about 135 breakages across `ocr.py`, the OCR child and answer checks in `isolation.py`, the route, the settings and the start-up check. Each survivor was a missing test (the probe's environment, the exact size limits, a plain space inside a word, using the right page's text layer and size, the 4 000 px cap, the confidence limits, a path of exactly 4 096 characters) and tests were added until all were caught, apart from equivalent cases: the deadline test at exactly zero seconds left, bad UTF-8 (which fails the header check anyway), a redundant guard (an empty text layer already has no agreement), a second word cap that `assemble_ocr` repeats, and `Path(".")` for the working directory.
8. **Not done:** deciding when to run OCR (page 1 of every PDF, pages marked `NeedsCheck`) belongs to the job code that will call the worker, with the verdict from `text_quality` (step 6); masking (step 5); the Rust client (step 7). The Debian 13 package (Tesseract 5.5.0) was used for the real runs.

**Step 5, `POST /v1/mask`:**
1. **The call.** `POST /v1/mask?format=png&max_edge=2000` with a JSON body `{"image": "<base64 of a PNG or JPEG>", "boxes": [{"x","y","w","h"}, ...]}` and the answer is the picture with the boxes painted solid black (`image/png` or `image/jpeg`, with `X-Image-Width`, `X-Image-Height` and `Cache-Control: no-store`, like `/v1/render`). **The body is JSON, not "a PNG and a list of boxes" as the table in section 2 puts it**: 500 boxes do not fit in a query string or a header, and a JSON body lets the request be checked field by field (exact whole numbers, no extra keys, at most 500 boxes, each inside the picture) without a multipart parser. The picture may be up to 16 MiB; the pictures the worker draws are far smaller. The base64 must be plain (no line breaks or other characters) and the content type the caller claims is never asked for.
2. **No rules.** The worker is told which rectangles and paints them; which words are personal data, and how much margin to leave around a word, is decided in `clearcut-core`. A box is in thousandths of the picture from its top left, the same unit as the word boxes the text and OCR answers give, so they can be passed straight on. It is turned into pixels **rounded outwards** (a box never covers less than asked, and always at least one pixel) and painted pure black, edge pixels included. A picture is turned upright from its EXIF orientation first, so the boxes mean what they meant on the picture the worker drew.
3. **Nothing survives.** The result is built from pixels only (as for rendering), so nothing that was under a box is in it, and neither is any metadata or an alpha channel of the picture it came from (transparency is mixed into white before the painting, so it cannot be used to keep what was painted over). A test with a picture whose every pixel differs checks that after painting it all, every pixel is black.
4. **Isolation.** It decodes a hostile picture, so it runs in the same kind of child as the other calls, and the parent measures the answer the same way (size, opening and closing bytes, the size the picture states for itself) without decoding it. Only PNG and JPEG are accepted (`415` otherwise); a damaged picture is `422`, one over 40 million pixels `422` "the image is too large", and the picture limit is `413`.
5. **What is left for the Rust side (step 7):** `WorkerMasker`, the `ImageMasker` of ADR-0014, turns the redaction spans into word boxes through the OCR or text words, adds the margin, calls this and gets the masked picture. An OCR-read page is the only way to mask a scanned page, which is why the order was OCR first.
6. **Mutation check:** about 80 breakages across `mask.py`, the request checks in `app.py` and the child. Survivors were missing tests (boxes given as lists, the byte limit passed on, the deadline around opening, base64 with stray characters, the exact picture limit, the child bringing a big picture down to the edge, the parent rejecting an answer that is too big, the default answer cap) and are covered now. The rest are equivalent: a check repeated one level down (the picture type, the empty picture after the base64 check, the upper limits of x and w that the box validator repeats) and two of those were removed as dead code.

**Step 6, `text_quality` in `clearcut-core`:**
1. **What it is.** A pure module (`clearcut_core::text_quality`, no input or output) that takes the evidence the worker reports, which is the page's text layer, its fonts and, if OCR was run, the OCR agreement, and returns a **verdict** (`Good`, `NeedsCheck`, `Unusable`), the **reasons** for it in a fixed vocabulary, and the **measures** it rests on. No text is ever in the answer. Everything is integer arithmetic (shares in thousandths), so the same evidence always gives the same answer. The worker's font facts are read here with the exact names it writes (`FontFact`, strict: an unknown value or extra field is refused).
2. **The measures** (section 4's list): non-white-space characters; replacement (U+FFFD) and private-use characters; control characters; letters, digits and punctuation or symbols (ASCII punctuation, currency signs and the usual typographic punctuation) as shares; words of three letters or more written in Latin letters, how many of them have no vowel (`y`, and accented vowels in Latin-1 and Latin Extended, count) and how many have a capital inside them; the longest unbroken run; and how many of 19 invoice keywords (English and Afrikaans) appear, each once. Words in other scripts are not judged by Latin vowels.
3. **The verdict**, in this order. No text: `Unusable`. Five percent or more replacement or private-use characters, or an OCR agreement under 500: `Unusable` (both reasons are given if both apply). Otherwise, if OCR was run, the agreement alone decides: 850 or more `Good` (whatever the fonts say), under that `NeedsCheck`. With no OCR result: a risky font (Type 3, or a custom or identity encoding with no Unicode map) **and** weak text (no keyword, or more than three in ten words without a vowel) is `NeedsCheck`; anything else is `Good`. All the thresholds are constants marked provisional until real obfuscated samples and a gold-set run exist (P2-20).
4. **What it does not claim**, tested on purpose: a scramble of the alphabet from fonts that look ordinary is not caught by the text alone, and digits swapped for other digits look like valid text. The text measures are one layer; the others are the page image the model reads, the totals re-derived to the cent, and the OCR agreement, which is what settles both of those cases (tests show swapped digits go to `NeedsCheck` or `Unusable` once the agreement is known).
5. **Which decision uses it** is for the job code (step 7 and P2-14): page 1 of every PDF gets the OCR agreement as a sentinel, `NeedsCheck` pages get it, and an `Unusable` page is read from OCR and recorded as `text_layer_rejected`. This module only decides what the evidence says.
6. **Mutation check:** about 85 breakages: the thresholds one either side, the font rule, each range of the character classes, the vowel set, the decision order. Survivors were boundary characters that no test touched; a table of every range edge and of each accented vowel now covers them. Two checks that could never matter were simplified (U+3000 is white space, so the punctuation range starts after it; a Latin-letter test that only ever sees letters). The tool `cargo-mutants` was not installed and was not added; the same breakages were made by hand with the harness used for the Python code.

**Step 7, the Rust side of the worker boundary** (`clearcut-docproc`):
1. **The trait.** `DocumentProcessor` gains `page_texts(document, PageRange, words)`, `ocr_page(document, page, agreement)`, `render_page(document, page, RenderOptions)` and `mask_image(image, boxes, format, max_edge)`. The request types can only hold what the worker accepts (`PageRange` of at most 50 pages, `RenderOptions` with dpi 100 to 300 and an edge of 500 to 2 576, `MaskBox` inside the picture and at most 500 of them), so a request the worker is certain to refuse fails where it is made, not as an HTTP error. The worker still checks again. `DocumentKind` is now `Pdf`, `Png` or `Jpeg`.
2. **What comes back is checked as hard as it was sent.** `PageContent` and `RenderedPage` can only be built from values that pass the same rules the worker applies (text of at most 1 MiB, at most 20 000 words, word offsets on character boundaries, boxes inside the page, a source that fits the words; a picture whose opening bytes, closing bytes and stated size agree and whose long side is at most 2 576 pixels). Their `Debug` shows sizes only, never text or bytes.
3. **`HttpWorker`** reads text answers up to 32 MiB, pictures up to 6 MiB and error answers up to 64 KiB, and decodes the JSON field by field (`http/wire.rs`): fields it does not know are ignored so the worker can add one, every field it does know must be exactly what was promised, the pages must be exactly those asked for and in order, words must be present exactly when asked for, and an OCR answer must say `ocr`, a text answer must not, and an agreement nobody asked for is not believed. A picture's own headers (`Content-Type`, `X-Image-Width`, `X-Image-Height`) must agree with its bytes, and neither side may be longer than the `max_edge` that was asked for. Redirects are still refused. Nothing the worker said is ever repeated in an error.
4. **Errors.** `422 "the page range is outside the document"` becomes `DocumentProblem::PageOutOfRange { pages }` (the page count is the `pages` field of the worker's error body; without a usable one the document is `Unreadable`); a page with too much text is `PageTooLarge`, a page too big to draw is `PageTooBig`, a picture over the pixel limit is `ImageTooLarge`. `503 "OCR is not available"` is the new `ProcessError::NotAvailable`, which maps to `FailureKind::ProviderUnavailable` (a worker without OCR is an operating problem, never a verdict on the document). All other mappings are unchanged.
5. **`FakeWorker`** takes a script per method (`with_texts`, `with_ocr`, `with_renders`, `with_masks`; `answering` for the simple case), answers in order, and records every call (`TextCall`, `OcrCall`, `RenderCall`, `MaskCall`) so a test can say what was asked. An empty script answers `Unexpected { status: 0 }`, never a made-up success.
6. **`WorkerMasker` and a deviation from "implements `ImageMasker`" simply.** The pack builder asks for a masked picture synchronously while it builds; the worker is a network call. So `WorkerMasker::prepare(...)` is `async`: it makes the worker call up front for the redaction spans the builder is about to compute (redaction is a pure function of the text, so the caller can compute the same ones), and the masker it returns implements `ImageMasker::mask` by handing over the prepared picture, **only if** it is asked about exactly the same picture, text and spans. Anything else is `MaskError::Failed`, so a mismatch can only make a page less sendable (the strict policy then routes it to review), never let a number through. `tests/masker_pack.rs` runs it through the real `build_pack_with_nonce`: a masked state, an unmasked page on mismatch, and strict refusing.
7. **Which words are boxed.** A redaction span is a range of bytes of the page text; every word the span touches, even partly, is boxed whole, with a margin of 3 thousandths on every side (`MASK_MARGIN_PER_MILLE`), kept inside the picture. A span is only painted if the words cover **all** of it: every character in it that is not white space must lie inside some word, and it must sit on character boundaries inside the text (found in the automated security review: touching one word was enough at first, which would have left the rest of a value visible if the worker ever reported fewer words than the text holds). A span that touches no word, runs past the words, or needs more than 500 boxes is an error and never a quiet omission (the same rule as the pack's strict policy: send nothing rather than a picture with a number still in it). `boxes_for_spans` therefore takes the page text as well. The picture that comes back keeps the kind the worker returned (a PNG that was too big may come back as a JPEG).
8. **Tests.** 142 in the crate (39 before) and 4 integration tests with the pack builder, all without a key. 14 live contract tests (`cargo test -p clearcut-docproc --test live -- --ignored`) run against the real worker in CI; the contract job now installs Tesseract (`eng`, `afr`) and starts the worker with `CLEARCUT_WORKER_TESSERACT`, so the OCR contract is exercised (a worker without OCR must answer `NotAvailable`, a worker with it must read the page).
9. **Mutation check:** about 185 breakages by hand (cargo-mutants is not installed and was not added). The first pass let through 14 and a later one (the coverage rule) 1, each a missing test (the absolute 2 576 / 2 577 edge, a word that does not belong to the page, a changed picture kind, the position and confidence of a parsed word box, a text-shaped answer to an OCR call and the other way round, the response size limits, the content type of a mask request, the page-range error mapping, the empty-script answer) and all are caught now. Three survivors are equivalent and left: the 64 KiB cap on error answers only bounds memory, and two picture-header checks (an empty value, a wrong length) are rejected one step later anyway.
10. **Not done, by design:** deciding when to run OCR and how to use the `text_quality` verdict (page 1 of every PDF as a sentinel, `NeedsCheck` pages, `text_layer_rejected`) belongs to the pipeline and router (P2-14). The container (P1-07) and resumable uploads are untouched.

## Alternatives considered
- *Keep PyMuPDF.* Best-in-class, but AGPL; rejected for an Apache-2.0 project.
- *Send the PDF straight to Claude.* The API accepts PDFs, but it gives the model the raw file, gives us no say about scrambled text layers, and defeats redaction (research 06 §7).
- *Decide the verdict in the worker.* Faster to write, but then thresholds and word lists are business rules in the wrong language and the wrong repository layer.
- *OCR every page every time.* The strongest independent read, at a CPU cost on every page of every document; the vision read plus the P2-13c cross-check already give an independent check, so OCR is used where there is evidence of trouble and on page 1 as a sentinel.
- *A stateful worker that keeps uploaded files.* Fewer bytes on the wire, but it keeps other people's documents between calls; deferred until measured.
